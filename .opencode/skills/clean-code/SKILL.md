# Чистый код Eggpipe

Используй этот skill при написании нового кода, рефакторинге и code review.
Цель — код, который легко читать, менять и тестировать, а не «умный» код.
Для выбора паттернов, value objects и стратегий используй `python-patterns`.

## Принципы

1. **Читаемость важнее краткости.** Код читают чаще, чем пишут. Явный цикл лучше
   многострочного comprehension с двумя условиями.
2. **Одна функция — одна причина для изменения.** Если функция делает discovery,
   валидацию и запись — это три функции.
3. **Плоско, а не глубоко.** Больше двух уровней вложенности `if`/`for` — сигнал
   к guard clauses и ранним возвратам.
4. **Явное лучше неявного.** Не прячь важное поведение в `*args`, `getattr`,
   `except Exception` и побочные эффекты вспомогательных функций.
5. **Типы — часть дизайна.** `dict[str, Any]`, `tuple[...]` из трёх `set | None`
   и `Any` в публичных сигнатурах означают, что не хватает модели.
6. **Неизменяемость по умолчанию.** Входы плагинов и доменные модели не мутируются.
   Локальная мутация допустима, скрытая — нет.
7. **Границы слоёв.** CLI не содержит бизнес-правил, Engine не занимается I/O-деталями,
   core не импортирует CLI/engine. Плагин не пишет файлы.
8. **Ошибки — часть контракта.** Доменная ошибка с кодом лучше `None` или `print`.
   `except Exception: continue` допустим только с диагностикой и обоснованием.
9. **Дублирование хуже преждевременной абстракции.** Два одинаковых блока — повод
   вынести helper; два похожих, но разных — оставить явными.
10. **Комментарий объясняет «почему», а не «что».** Код должен читаться без пересказа.

## Ветвления

Плохой код:

```python
if exists:
    if owned:
        if on_conflict == "skip":
            ...
        else:
            ...
    else:
        if force:
            ...
```

Хороший код:

```python
if not exists:
    return _create(...)
if _is_owned(...):
    return _write_owned(...)
if not force:
    return _reject_foreign(...)
return _overwrite_foreign(...)
```

Правила:

- Сначала обрабатывай выходные условия (`return`, `continue`, `raise`).
- Не пиши `if cond: pass` и `elif ...: pass` — это скрытая пустая ветка.
- Не дублируй одну проверку на нескольких уровнях. Если `on_conflict == "error"`
  обработан выше, ниже его быть не должно.
- Булев флаг в сигнатуре (`dry_run`, `force`, `strict`) допустим, если он меняет
  одно понятное решение. Три и более флага — повод для объекта параметров.
- `match` используй для вариантов одного значения, а не как замену `if`.

## Константы

- Именованная константа нужна, если значение:
  - повторяется в нескольких местах;
  - имеет доменный смысл (`MAX_IMPORT_DEPTH`, `GENERATOR_GROUP`);
  - должно меняться централизованно (`REPORT_VERSION`).
- Не выноси в константы одноразовые строки, которые читаются лучше на месте.
- Не создавай «константу ради константы» с именем, повторяющим значение.
- Коды диагностик (`MGxxx`) — стабильный доменный словарь. Держи их в одном модуле
  или именованных константах, если они используются повторно; не изобретай новый код
  для того же смысла.
- Политики (`Literal["off", "prompt", "enabled"]`) выноси в type alias и используй
  его в сигнатурах, а не повторяй строковый литерал.

## Модели и данные

- Три и более связанных значения — `dataclass`/Pydantic-модель, а не кортеж.
- `dict[str, Any]` на границе функции — признак отсутствующей модели.
- Sentinel (`UNSET`) лучше `None`, если «не задано» и «пусто» — разные состояния.
- Для перечислений используй `StrEnum`/`Literal`; не сравнивай «магические» строки
  в десяти местах.
- Не возвращай `None` для ошибки и значение для успеха в одной функции без
  документированного контракта.

## Функции и классы

- Держи функцию в пределах ~40 строк и ~5 параметров. Больше — дели.
- Публичная функция начинается с глагола (`select_slice`, `validate_document`),
  модель — с существительного.
- Не смешивай вычисление и побочный эффект: `_collect_*` не должна писать файлы,
  `_write_*` не должна вычислять бизнес-правила.
- Скрытое состояние (`self._composition`) допустимо только внутри одного сценария.
  Если метод зависит от «магии» предыдущего вызова — передавай зависимость явно.
- `__init__` не должен выполнять I/O, если объект создаётся в тестах.

## Обработка ошибок

- Лови конкретные исключения. `except Exception` — только на границе плагина/watch,
  с логированием или диагностикой.
- Не глотай ошибку молча: `except Exception: continue` без сообщения запрещён.
- Не используй exception для управления обычным потоком.
- В CLI одна точка преобразования доменных ошибок в exit code; не копируй
  одинаковые `try/except` в каждую команду.
- Диагностика должна содержать код, уровень, сообщение и локацию.

## Python-детали

- `Path` вместо строковых путей; `PurePosixPath` для путей артефактов.
- Не используй изменяемые значения по умолчанию (`[]`, `{}`, `set()`).
- Comprehension — один уровень и одно условие; иначе обычный цикл.
- Не пиши `if x is not None and x != y` там, где достаточно `if x not in (None, y)`.
- Избегай `type: ignore`, если можно сузить тип; каждый ignore — с причиной.
- Ленивый импорт допустим для optional-зависимостей; для внутреннего модуля
  добавь комментарий, почему импорт не наверху.

## Чек-лист ревью

### Читаемость

- [ ] Имя функции/переменной объясняет смысл без комментария.
- [ ] Нет функции длиннее ~40 строк и вложенности глубже 2–3 уровней.
- [ ] Нет `pass`-веток, мёртвых условий и недостижимого кода.
- [ ] Нет дублирующихся блоков `try/except`, фильтрации и построения моделей.

### Данные и контракты

- [ ] Нет `dict[str, Any]` и кортежей-«структур» там, где нужна модель.
- [ ] Публичные сигнатуры типизированы; `Any` обоснован.
- [ ] Доменные строки/политики вынесены в `Literal`/`StrEnum`/константы.
- [ ] Входы не мутируются; побочные эффекты видны из имени.

### Ветвления и константы

- [ ] Выходные условия обрабатываются рано.
- [ ] Одна проверка не повторяется на разных уровнях.
- [ ] Константы имеют доменный смысл, а не дублируют литерал.
- [ ] Нет магических чисел/строк, повторяющихся больше двух раз.

### Границы и ошибки

- [ ] CLI тонкий; бизнес-правила в Engine/core.
- [ ] core не зависит от CLI/engine; плагины не пишут файлы.
- [ ] Ошибки конкретные; нет молчаливых `except Exception`.
- [ ] Exit codes и диагностика формируются в одном месте.

### Тесты

- [ ] Новая ветка покрыта тестом на поведение, а не на реализацию.
- [ ] Тесты используют фабрики/фикстуры, а не копипасту больших словарей.
- [ ] Контрактные тесты проверяют публичный API, а не приватные детали.

## Формат отчёта

Для каждой находки:

- **Severity:** `Blocker` (баг/потеря данных), `Major` (трудно менять/тестировать),
  `Minor` (читаемость/дублирование), `Nit` (стиль).
- **Где:** `path:line`.
- **Проблема:** что именно мешает и почему.
- **Предложение:** конкретный рефакторинг, без «переписать всё».

В конце: краткий план по приоритетам и список проверенных файлов.
Не меняй код в рамках read-only ревью без отдельного разрешения.
