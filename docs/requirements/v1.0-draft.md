# Метаинформационный генератор — Техническое задание

## 1. Цель и назначение

**Назначение:** инструмент командной строки (CLI), который читает описание модели данных из файла формата YAML и порождает из него артефакты в произвольных целевых форматах (SQL-миграции, JSON-схемы, YAML-конфиги, Python-модели, TypeScript-типы и т.п.).

**Ключевая философия:** один источник истины — YAML-описание модели — произвольное количество генераторов-«адаптеров», каждый из которых умеет превращать одну и ту же модель в свой формат.

**Целевая аудитория:** fullstack-команды, разработчики API-first сервисов, инженеры, которым нужно поддерживать консистентность между схемой базы данных, спецификацией API и клиентскими типами.

---

## 2. Термины и определения

| Термин               | Определение                                                                 |
|----------------------|-----------------------------------------------------------------------------|
| **Документ модели**  | Файл, содержащий описание модели. Включает метаданные (`format`, `version`, `updated_at`) и секцию `model` с описанием сущностей |
| **Исходная модель**  | Секция `model` внутри документа — структура данных (сущности, поля, связи, ограничения). Может существовать только внутри документа |
| **Генератор**        | Плагин, преобразующий исходную модель в целевой формат                      |
| **Шаблон**           | Jinja2-шаблон, используемый генератором для рендеринга вывода              |
| **Артефакт**         | Результат работы генератора — файл или поток данных в целевом формате        |
| **Мета-конфиг**      | YAML-файл с настройками: какие генераторы запускать, куда класть результат   |

---

## 3. Формат исходной модели (YAML)

### 3.1. Структура документа

Документ состоит из **метаданных** и секции **model**. Метаданные определяют парсер (через `format`), секция `model` — данные.

```yaml
# === Метаданные документа (обязательные) ===
format: entity-model     # Тип документа. Определяет какой парсер использовать.
                         # Не влияет на выбор генераторов.
extends: base            # Родительский тип (опционально). Поддерживается наследование.
version: "1.0"           # Версия схемы формата (не модели!)
updated_at: "2025-11-03" # Дата последнего изменения в ISO 8601

# === Описание модели ===
model:
  name: string           # Имя модели
  description: string    # Опциональное описание

  entities:              # Сущности (универсальное понятие)
    - name: string       # Имя сущности
      description: string
      fields:
        - name: string              # Имя поля
          type: string              # Тип данных (примитивный или ссылка на enum/type)
          description: string
          required: boolean         # Обязательность (по умолчанию false)
          default: string | number | null | auto  # Значение по умолчанию (auto = автогенерация)

  enums:                            # Перечисления
    - name: string
      description: string
      values:
        - name: string
          value: string | number    # Опциональное значение (по умолчанию = name)
          description: string

  types:                            # Пользовательские типы (алиасы)
    - name: string                  # Имя типа
      base: string                  # Базовый тип (примитивный)
      constraints:                  # Ограничения (для валидации)
        min: number
        max: number
        min_length: number
        max_length: number
        pattern: string             # Регулярное выражение
```

### 3.2. Примитивные типы данных

| Тип          | Описание                        |
|--------------|---------------------------------|
| `string`     | Строка                          |
| `text`       | Длинный текст                   |
| `integer`    | Целое число                     |
| `bigint`     | Большое целое                   |
| `boolean`    | Логический тип                  |
| `float`      | Число с плавающей точкой        |
| `date`       | Дата                            |
| `datetime`   | Дата и время                    |
| `uuid`       | UUID                            |
| `json`       | JSON-объект                     |

> **Примечание:** Это минимальный набор. Конкретные парсеры могут добавлять свои типы (например, SQL-парсер добавит `serial`, `decimal`, `inet` и т.д. через наследование).

### 3.3. Правила разрешения типов

- Тип, совпадающий с именем `enum` или `type` из модели, раскрывается в их определение
- Если тип не опознан, парсер выбрасывает ошибку

### 3.4. Принцип наследования типов

Тип документа наследуется через поле `extends`. Это позволяет расширять базовую схему.

```yaml
# Пользователь создаёт свой тип с SQL-спецификой
format: sql-model
extends: entity-model
version: "1.0"
updated_at: "2025-11-03"

# В секции model можно добавлять поля, специфичные для sql-model
# Парсер sql-model понимает: entities[].relations, on_delete, indexes и т.д.
```

**Правила:**
- `extends` опционально
- Дочерний тип получает все поля родительского
- Дочерний тип может добавлять свои поля
- Циклические зависимости запрещены
- Глубина наследования — минимум 3 уровня

**Базовый тип `entity-model`:**
```yaml
format: entity-model
extends: base
version: "1.0"
```

Минимальный набор полей: `name`, `description`, `entities`, `enums`, `types`.

### 3.5. Композиция данных (Composition)

Сущности можно хранить в одном файле или распределять по нескольким файлам/каталогам.

#### 3.5.1. Варианты хранения сущностей

**Вариант 1: Monolith (всё в одном файле)**
```
model.yaml           # Все entities, enums, types в одном файле
```

**Вариант 2: File-per-entity (файл на сущность)**
```
entities/
  user.yaml          # entity: User
  post.yaml          # entity: Post
  tag.yaml           # entity: Tag
common/
  enums.yaml         # shared enums
  types.yaml         # shared types
```

**Вариант 3: Directory-per-entity (каталог на сущность)**
```
entities/
  user/
    model.yaml       # entity: User
    avatar.svg       # ресурсы для генерации
    description.md   # документация
  post/
    model.yaml       # entity: Post
    template.html    # ресурсы для генерации
```

#### 3.5.2. Imports внутри entity

Сущность может подключать внешние файлы двух типов:

**Импорт YAML-моделей** — для композиции/наследования:
```yaml
format: entity-model
model:
  imports:
    - path: ./base-entity.yaml    # импорт общей базовой структуры
    - path: ../shared/audit.yaml  # импорт audit-полей
  entities:
    - name: Post
      extends: ./base-entity.yaml # наследование от импортированного
      fields:
        - name: title
          type: string
```

**Импорт произвольных файлов** — для использования при генерации:
```yaml
format: entity-model
model:
  imports:
    - path: ./icons/user.svg      # файл для генерации
      as: avatar_icon             # имя для обращения в шаблоне
    - path: ./templates/card.html
      as: card_template
  entities:
    - name: User
      fields:
        - name: avatar
          type: string
```

Импортированные файлы доступны генератору в контексте entity:
```
entity.imports["avatar_icon"]  → содержимое icons/user.svg
entity.imports["card_template"] → содержимое templates/card.html
```

#### 3.5.3. Правила импорта

- Пути разрешаются относительно файла, где описан `import`
- Поддерживаются относительные пути (`./`, `../`)
- Циклические импорты запрещены (проверяется при парсинге)
- Импорты из родительских файлов наследуются

## 4. Принцип «данные отделимы от генерации»

Ключевая идея: **модель — это просто данные**. Нет жёсткой привязки «тип модели» → «генераторы».

Пользователь описывает данные один раз, а в метакогфиге решает:
- Какие сущности взять из модели
- Какие генераторы применить
- Какие enum'ы и типы включить

Один и тот же набор сущностей может порождать разные артефакты в разных генераторах.

## 5. Структура метакогфига

> **Примечание:** Генераторы создаются под конкретный проект/стек. Инструмент обеспечивает только механизм подключения генераторов и передачи им данных. Реализация генераторов — часть проекта.

```yaml
version: "1.0"

# Глобальные параметры модели
defaults:
  naming_convention: snake_case  # snake_case | camelCase | kebab-case | pascal_case
  required_by_default: false

# Источники данных
sources:
  - path: ./models/main.yaml      # Путь к файлу/каталогу модели
    entities: []                  # Какие сущности брать (пусто = все)
    enums: []                     # Какие enum'ы брать (пусто = все)
    types: []                     # Какие типы брать (пусто = все)

# Подключение генераторов
generators:
  - id: oracle-ddl                # ID генератора (задаётся при создании)
    enabled: true
    source: ./models/main.yaml
    input:
      entities: [User, Post]      # Подмножество сущностей для этого генератора
      enums: [PostStatus]
    output_dir: ./output/oracle
    file_naming: "{entity_name}.sql"
    options:                      # Опции зависят от генератора
      tablespace: USERS
      storage: ASSM

  - id: snowflake-schema
    enabled: true
    source: ./models/main.yaml
    input:
      entities: [User, Post]
    output_dir: ./output/snowflake
    options:
      warehouse: COMPUTE_WH
      database: ANALYTICS
```

### 5.1. Подключение генератора

Каждый генератор — это **плагин**, который:
- Имеет уникальный `id`
- Реализует интерфейс (детали — в документации разработчика)
- Подключается к инструменту через механизм расширений (entry points / конфигурация)
- Получает данные модели через `sources` и `input`

> Детали реализации плагинов (API, интерфейсы, жизненный цикл) — в документации разработчика, а не в данном ТЗ.

## 6. Шаблонизация

> **Примечание:** Механизм шаблонизации определяется генератором. Инструмент обеспечивает только передачу данных в шаблон.

Каждый генератор может:
- Использовать свой движок шаблонизации (Jinja2, Mako, etc.)
- Поставлять шаблоны внутри плагина
- Позволять пользователю переопределять шаблоны через конфигурацию

Пример переопределения шаблона (если генератор поддерживает):

```yaml
generators:
  - id: my-generator
    templates:
      main: ./my-templates/output.j2
      partial: ./my-templates/partial.j2
```

## 7. CLI-интерфейс

### 7.1. Синтаксис команд

```bash
# Основные команды
mg generate <model.yaml>              # Генерировать всё (по умолчанию)
mg generate <model.yaml> --all        # Явно всё
mg generate <model.yaml> --generator sql-create,python-pydantic  # Только指定ные
mg generate <model.yaml> --output ./custom-output

# Конфигурация
mg init                               # Создать шаблон метакогфига .mg.yaml
mg config show                        # Показать текущую конфигурацию
mg config validate                    # Валидировать конфигурацию

# Информация
mg list-generators                    # Список доступных генераторов
mg list-templates                     # Список встроенных шаблонов
mg model validate <model.yaml>        # Валидировать модель без генерации

# Режим watch (dev-режим)
mg watch <model.yaml>                 # Следить за изменениями и перегенерировать

# Подстановки переменных окружения
mg generate <model.yaml> \
  --var DB_HOST=localhost \
  --var DB_PORT=5432 \
  --set generators[0].options.dialect=sqlite
```

### 7.2. Флаги

| Флаг                        | Описание                                         |
|-----------------------------|--------------------------------------------------|
| `--config`, `-c`            | Путь к метакогфигу (по умолчанию `.mg.yaml`)     |
| `--generator`, `-g`         | Список генераторов через запятую                |
| `--output`, `-o`            | Корневая директория для артефактов              |
| `--var KEY=VALUE`           | Переменные окружения для подстановки в шаблоны  |
| `--set`                     | Переопределение параметров генератора            |
| `--watch`, `-w`             | Режим наблюдения за изменениями файлов           |
| `--dry-run`                 | Показать результат без записи файлов             |
| `--format`                  | Формат вывода CLI: `text` (default) или `json`  |
| `--verbose`, `-v`           | Подробный вывод                                  |
| `--quiet`, `-q`             | Только ошибки                                    |

## 8. Валидация

### 8.1. Валидация исходной модели

Валидация выполняется **до** генерации и включает:

| Проверка                                | Серьёзность    |
|-----------------------------------------|----------------|
| Синтаксис YAML                          | Error          |
| Корректность типов данных               | Error          |
| Ссылки на несуществующие сущности в relations | Error    |
| Ссылки на несуществующие enum/type       | Error          |
| Дублирующиеся имена сущностей/полей     | Error          |
| Корректность regex в constraints.pattern | Error         |
| Пустые обязательные поля                | Warning        |
| Неиспользуемые enum/type                | Warning        |
| Потенциально небезопасные default-значения | Warning      |

### 8.2. Валидация результатов генерации

Каждый генератор может (и должен) валидировать свой вывод:

- **SQL-генераторы** — результат парсится обратно, проверяется синтаксис
- **TypeScript-генератор** — результат проверяется через `tsc --noEmit`
- **Python-генераторы** — результат проверяется через `mypy` / `pyright`
- **JSON Schema** — валидация через `jsonschema` library

Ошибки валидации выводятся, но **не блокируют** генерацию (с флагом `--force`).

## 9. Архитектура

Архитектура состоит из двух независимых частей: **ядро** (metadata-generator) и **плагины** (генераторы).

### 9.1. Ядро (metadata-generator)

Ядро — это инструмент, который читает модели и координирует генерацию.

```
metadata-generator/              # Основной пакет (pip install metadata-generator)
├── src/metadata_generator/
│   ├── cli/                     # CLI-слой
│   │   ├── commands.py
│   │   └── formatters.py
│   ├── core/                    # Парсинг, валидация, composition
│   │   ├── model.py             # Модель данных (Entity, Field, Enum)
│   │   ├── parser.py            # Парсинг YAML + imports + extends
│   │   ├── validator.py         # Валидация модели
│   │   └── composition.py       # Объединение данных из нескольких файлов
│   ├── engine/                  # Движок генерации
│   │   ├── engine.py            # Orchestration: загрузка плагинов, запуск генерации
│   │   ├── plugin_loader.py     # Загрузка плагинов (entry points)
│   │   └── artifact_writer.py   # Запись артефактов в файловую систему
│   └── utils/
│       └── logging.py
├── pyproject.toml
└── README.md
```

**Ядро не содержит генераторов и шаблонов.** Оно только:
- Парсит и валидирует модели
- Загружает плагины-генераторы
- Передаёт данные в плагин
- Записывает результат

### 9.2. Плагин (генератор)

Каждый генератор — отдельный Python-пакет. Содержит логику генерации и свои шаблоны.

```
my-oracle-generator/             # Пример плагина-генератора
├── pyproject.toml               # entry point для загрузки
├── src/my_oracle_generator/
│   ├── __init__.py              # GeneratorPlugin implementation
│   ├── templates/               # Шаблоны генератора
│   │   ├── entity.sql.j2
│   │   └── table.sql.j2
│   └── assets/                  # Дополнительные ресурсы (опционально)
├── README.md
└── tests/
```

**Плагин предоставляет:**
- Код генератора (реализует интерфейс генератора)
- Шаблоны (могут быть переопределены пользователем)
- Ресурсы (иконки, etc.)

### 9.3. Поток данных

```
┌─────────────────────────────────────────────────────────────────┐
│                           ЯДРО                                   │
│                                                                 │
│   CLI ──► Парсинг ──► Валидация ──► Composition ──► [Model]    │
│                                                     │           │
│                              Загрузка плагинов ──────┘           │
│                                      │                          │
└──────────────────────────────────────┼──────────────────────────┘
                                       │
                              ┌────────▼────────┐
                              │    ПЛАГИН 1     │
                              │  (генератор)    │
                              │                 │
                              │  Получает Model │
                              │  Возвращает:    │
                              │  [Artifact]     │
                              └────────┬────────┘
                                       │
                              ┌────────▼────────┐
                              │    ПЛАГИН 2     │
                              │  (генератор)    │
                              └─────────────────┘
```

### 9.4. Стек технологий

| Компонент        | Технология                                    |
|------------------|-----------------------------------------------|
| CLI              | Click или Typer                               |
| YAML-парсинг     | PyYAML или ruamel.yaml                        |
| Загрузка плагинов | Entry points (pip entry_points) или конфиг  |
| Типизация        | Pydantic / dataclasses + typing                |
| Конфигурация     | pydantic-settings (рекомендуется)             |
| Тестирование     | pytest (+ hypothesis для property-based)       |
| Установка        | pip / uv / poetry                              |

### 9.5. Конфигурация

Конфигурация разделена на два слоя:

#### 9.5.1. Application Config (технический)

Настройки работы приложения: логирование, пути, debug mode, источники конфигурации.

```python
# config.py (пример)
from pydantic_settings import BaseSettings

class Settings(BaseSettings):
    debug: bool = False
    log_level: str = "INFO"
    plugins_dir: Path = Path("./plugins")
    cache_enabled: bool = True
    
    class Config:
        env_prefix = "MG_"
        env_file = ".env"
```

**Источники конфигурации:**
1. Environment variables (`MG_DEBUG=true`)
2. `.env` файл
3. Файл конфигурации (если есть)
4. Значения по умолчанию

#### 9.5.2. Business Config (`.mg.yaml`)

Бизнес-конфигурация проекта: модели, генераторы, настройки генераторов (описано в секции 5).

## 10. Требования к качеству

### 10.1. Тестовое покрытие

- Минимум **80%** покрытия кода тестами
- Тесты на все встроенные генераторы (golden tests — сравнение с эталонным выводом)
- Property-based тесты через `hypothesis` для парсинга моделей
- Интеграционные тесты: полный цикл YAML → артефакт → валидация

### 10.2. Производительность

- Парсинг модели < 50 мс для файла до 1000 сущностей
- Генерация одного артефакта < 100 мс
- Суммарное время генерации всех встроенных генераторов < 5 секунд для модели из 50 сущностей

### 10.3. Документация

- Обязательно: README с примером использования
- Обязательно: примеры моделей (fixtures) для каждого генератора
- Обязательно: документация по формату модели и метакогфига
- Обязательно: руководство по созданию собственного генератора-плагина

## 12. Пример end-to-end

### 12.1. Входной файл: `model.yaml`

```yaml
format: entity-model
version: "1.0"
updated_at: "2025-11-03"
model:
  name: blog-platform
  entities:
    - name: User
      description: Пользователь блога
      fields:
        - name: id
          type: uuid
          required: true
        - name: email
          type: string
          required: true
        - name: username
          type: string
          required: true
          constraints:
            min_length: 3
            max_length: 50
        - name: created_at
          type: datetime
          required: true
          default: auto

    - name: Post
      description: Статья блога
      fields:
        - name: id
          type: uuid
          required: true
        - name: title
          type: string
          required: true
          constraints:
            min_length: 1
            max_length: 255
        - name: content
          type: text
          nullable: true
        - name: author_id
          type: uuid
          required: true
        - name: published_at
          type: datetime
          nullable: true
        - name: status
          type: PostStatus   # ссылка на enum
          required: true
          default: draft

  enums:
    - name: PostStatus
      values:
        - name: draft
          value: draft
        - name: published
          value: published
        - name: archived
          value: archived
```

### 12.2. Метакогфиг: `.mg.yaml`

```yaml
version: "1.0"

defaults:
  naming_convention: snake_case

sources:
  - path: ./model.yaml
    entities: [User, Post]        # Берём все сущности
    enums: [PostStatus]           # И enum

generators:
  - id: oracle-ddl                # Генератор под конкретный проект
    enabled: true
    input:
      entities: [User, Post]
    output_dir: ./output/oracle
    options:
      tablespace: USERS

  - id: snowflake-schema
    enabled: true
    input:
      entities: [User, Post]
    output_dir: ./output/snowflake
    options:
      warehouse: COMPUTE_WH
```
