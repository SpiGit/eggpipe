# Метаинформационный генератор — Техническое задание

## 1. Цель и назначение

**Назначение:** инструмент командной строки (CLI), который читает описание модели данных из файла формата YAML и порождает из него артефакты в произвольных целевых форматах (SQL-миграции, JSON-схемы, YAML-конфиги, Python-модели, TypeScript-типы и т.п.).

**Ключевая философия:** один источник истины — YAML-описание модели — произвольное количество генераторов-«адаптеров», каждый из которых умеет превращать одну и ту же модель в свой формат.

**Целевая аудитория:** fullstack-команды, разработчики API-first сервисов, инженеры, которым нужно поддерживать консистентность между схемой базы данных, спецификацией API и клиентскими типами.

---

## 2. Термины и определения

| Термин               | Определение                                                                 |
|----------------------|-----------------------------------------------------------------------------|
| **Документ модели**  | Файл, содержащий описание модели. Включает метаданные (`format`, `version`, `updated_at`) и секцию `model` с описанием сущностей |
| **Исходная модель**  | Секция `model` внутри документа — структура данных (сущности, поля, связи, ограничения). Может существовать только внутри документа |
| **Генератор**        | Плагин, преобразующий исходную модель в целевой формат                      |
| **Шаблон**           | Jinja2-шаблон, используемый генератором для рендеринга вывода              |
| **Артефакт**         | Результат работы генератора — файл или поток данных в целевом формате        |
| **Мета-конфиг**      | YAML-файл с настройками: какие генераторы запускать, куда класть результат   |

---

## 3. Формат исходной модели (YAML)

### 3.1. Структура документа

Документ состоит из **метаданных** и секции **model**. Метаданные определяют парсер (через `format`), секция `model` — данные.

```yaml
# === Метаданные документа (обязательные) ===
format: entity-model     # Тип документа. Определяет какой парсер использовать.
                         # Не влияет на выбор генераторов.
extends: base            # Родительский тип (опционально). Поддерживается наследование.
version: "1.0"           # Версия схемы формата (не модели!)
updated_at: "2025-11-03" # Дата последнего изменения в ISO 8601

# === Описание модели ===
model:
  name: string           # Имя модели
  description: string    # Опциональное описание

  entities:              # Сущности (универсальное понятие)
    - name: string       # Имя сущности
      description: string
      fields:
        - name: string              # Имя поля
          type: string              # Тип данных (примитивный или ссылка на enum/type)
          description: string
          required: boolean         # Обязательность (по умолчанию false)
          default: string | number | null | auto  # Значение по умолчанию (auto = автогенерация)

  enums:                            # Перечисления
    - name: string
      description: string
      values:
        - name: string
          value: string | number    # Опциональное значение (по умолчанию = name)
          description: string

  types:                            # Пользовательские типы (алиасы)
    - name: string                  # Имя типа
      base: string                  # Базовый тип (примитивный)
      constraints:                  # Ограничения (для валидации)
        min: number
        max: number
        min_length: number
        max_length: number
        pattern: string             # Регулярное выражение
```

### 3.2. Примитивные типы данных

| Тип          | Описание                        |
|--------------|---------------------------------|
| `string`     | Строка                          |
| `text`       | Длинный текст                   |
| `integer`    | Целое число                     |
| `bigint`     | Большое целое                   |
| `boolean`    | Логический тип                  |
| `float`      | Число с плавающей точкой        |
| `date`       | Дата                            |
| `datetime`   | Дата и время                    |
| `uuid`       | UUID                            |
| `json`       | JSON-объект                     |

> **Примечание:** Это минимальный набор. Конкретные парсеры могут добавлять свои типы (например, SQL-парсер добавит `serial`, `decimal`, `inet` и т.д. через наследование).

### 3.3. Правила разрешения типов

- Тип, совпадающий с именем `enum` или `type` из модели, раскрывается в их определение
- Если тип не опознан, парсер выбрасывает ошибку

### 3.4. Принцип наследования типов

Тип документа наследуется через поле `extends`. Это позволяет расширять базовую схему.

```yaml
# Пользователь создаёт свой тип с SQL-спецификой
format: sql-model
extends: entity-model
version: "1.0"
updated_at: "2025-11-03"

# В секции model можно добавлять поля, специфичные для sql-model
# Парсер sql-model понимает: entities[].relations, on_delete, indexes и т.д.
```

**Правила:**
- `extends` опционально
- Дочерний тип получает все поля родительского
- Дочерний тип может добавлять свои поля
- Циклические зависимости запрещены
- Глубина наследования — минимум 3 уровня

**Базовый тип `entity-model`:**
```yaml
format: entity-model
extends: base
version: "1.0"
```

Минимальный набор полей: `name`, `description`, `entities`, `enums`, `types`.

## 4. Принцип «данные отделимы от генерации»

Ключевая идея: **модель — это просто данные**. Нет жёсткой привязки «тип модели» → «генераторы».

Пользователь описывает данные один раз, а в метакогфиге решает:
- Какие сущности взять из модели
- Какие генераторы применить
- Какие enum'ы и типы включить

Один и тот же набор сущностей может порождать разные артефакты в разных генераторах.

## 5. Генераторы (плагины)

> **Примечание:** Инструмент не поставляется с генераторами «из коробки». Все генераторы создаются под конкретный проект/стек (Oracle, Snowflake, PostgreSQL, Pydantic, TypeScript и т.д.). Плагинная архитектура позволяет подключать любые генераторы.

### 5.1. Плагинная архитектура

Каждый генератор — это Python-пакет с интерфейсом `GeneratorPlugin`:

```python
from abc import ABC, abstractmethod
from dataclasses import dataclass

@dataclass
class GenerationResult:
    artifacts: list["Artifact"]

@dataclass
class Artifact:
    path: str           # Относительный путь файла
    content: str        # Содержимое файла
    mime_type: str      # MIME-тип (для подсказок IDE и tooling)

class GeneratorPlugin(ABC):
    @property
    @abstractmethod
    def id(self) -> str: ...

    @property
    @abstractmethod
    def name(self) -> str: ...

    @property
    def supported_model_versions(self) -> list[str]:
        return ["1.0"]

    @abstractmethod
    def generate(
        self,
        model: "SourceModel",
        config: "GeneratorConfig",
        context: "GenerationContext",
    ) -> GenerationResult: ...

    def validate(self, model: "SourceModel") -> list["ValidationError"]:
        return []
```

### 5.2. Жизненный цикл генерации

```
Чтение YAML модели
        │
        ▼
Парсинг → внутреннее представление (SourceModel)
        │
        ▼
Валидация модели (все генераторы)
        │
        ▼
Инициализация генераторов (по метакогфигу)
        │
        ▼
Для каждого генератора:
    ├── pre_generate hook (если определён)
    ├── apply_overrides (метакогфиг → параметры генератора)
    ├── generate() → Artifact[]
    └── post_generate hook (если определён)
        │
        ▼
Запись артефактов в файловую систему
        │
        ▼
Итоговый отчёт (что сгенерировано, warnings, errors)
```

### 5.3. Настройки генератора (метакогфиг)

```yaml
version: "1.0"

# Глобальные параметры модели (наследуются всеми генераторами)
defaults:
  naming_convention: snake_case  # snake_case | camelCase | kebab-case | pascal_case
  required_by_default: false

# Источники данных (общие для всех генераторов)
sources:
  - path: ./models/main.yaml      # Путь к файлу модели
    entities: []                  # Какие сущности брать (пусто = все)
    enums: []                     # Какие enum'ы брать (пусто = все)
    types: []                     # Какие типы брать (пусто = все)

generators:
  - id: oracle-ddl                # Генератор под конкретный проект/стек
    enabled: true
    source: ./models/main.yaml
    input:
      entities: [User, Post]      # Подмножество сущностей для этого генератора
      enums: [PostStatus]
    output_dir: ./output/oracle
    file_naming: "{entity_name}.sql"
    options:                      # Опции специфичны для генератора
      tablespace: USERS
      storage: ASSM
    hooks:
      pre: "hooks.pre_oracle"
      post: "hooks.post_oracle"

  - id: snowflake-schema
    enabled: true
    source: ./models/main.yaml
    input:
      entities: [User, Post]      # Другой набор — другие данные
    output_dir: ./output/snowflake
    options:
      warehouse: COMPUTE_WH
      database: ANALYTICS
```

## 6. Система шаблонов (Jinja2)

### 6.1. Где применяются шаблоны

Каждый генератор использует Jinja2-шаблоны для рендеринга артефактов. Шаблоны живут:

1. **Внутри генератора** — шаблоны, поставляемые с генератором
2. **В проекте пользователя** — пользовательские шаблоны, переопределяющие шаблоны генератора
3. **В отдельном репозитории** — шаблоны могут быть в git-submodule или внешнем пакете

### 6.2. Предоставляемые фильтры и функции Jinja2

```
Фильтры:
  {{ field.name | snake_case }}        → snake_case
  {{ field.name | camel_case }}        → camelCase
  {{ field.name | kebab_case }}        → kebab-case
  {{ field.name | pascal_case }}       → PascalCase
  {{ field.name | upper_case }}        → UPPER_CASE
  {{ field.name | plural }}            → множественное число
  {{ field.name | singular }}          → единственное число
  {{ type | to_sql(dialect) }}         → SQL-тип для диалекта
  {{ type | to_ts }}                   → TypeScript-тип
  {{ type | to_python }}               → Python-тип

Функции:
  {{ sql_type(field, 'postgresql') }}  → тип поля для конкретного диалекта
  {{ import_path(entity) }}            → путь импорта для генератора
  {{ constraints_sql(field) }}         → SQL-ограничения (CHECK, UNIQUE, etc.)
  {{ relations_sql(entity) }}          → SQL-foreign keys
  {{ field_default(field) }}           → дефолтное значение
```

### 6.3. Структура контекста в шаблоне

```jinja
{# Доступные переменные верхнего уровня #}
model               # SourceModel — вся модель целиком
entity              # Entity — текущая сущность (в итерации)
field               # Field — текущее поле (в итерации)
config              # GeneratorConfig — настройки текущего генератора
naming              # NamingHelper — утилиты именования

{# Пример: генерация Python/Pydantic #}
from pydantic import BaseModel, Field as PydanticField
{% for entity in model.entities %}
class {{ entity.name | pascal_case }}(BaseModel):
    """{{ entity.description or entity.name }}"""
    {% for field in entity.fields %}
    {{ field.name | snake_case }}: {{ field.type | to_python }}
        {% if field.required %}= Field(...) # required{% endif %}
    {% endfor %}
{% endfor %}
```

### 6.4. Переопределение шаблонов

Пользователь может переопределить любой шаблон через конфигурацию:

```yaml
generators:
  - id: sql-create
    templates:
      main: ./my-templates/sql-table.sql.j2
      partial_header: ./my-templates/partial/header.sql.j2
```

## 7. CLI-интерфейс

### 7.1. Синтаксис команд

```bash
# Основные команды
mg generate <model.yaml>              # Генерировать всё (по умолчанию)
mg generate <model.yaml> --all        # Явно всё
mg generate <model.yaml> --generator sql-create,python-pydantic  # Только指定ные
mg generate <model.yaml> --output ./custom-output

# Конфигурация
mg init                               # Создать шаблон метакогфига .mg.yaml
mg config show                        # Показать текущую конфигурацию
mg config validate                    # Валидировать конфигурацию

# Информация
mg list-generators                    # Список доступных генераторов
mg list-templates                     # Список встроенных шаблонов
mg model validate <model.yaml>        # Валидировать модель без генерации

# Режим watch (dev-режим)
mg watch <model.yaml>                 # Следить за изменениями и перегенерировать

# Подстановки переменных окружения
mg generate <model.yaml> \
  --var DB_HOST=localhost \
  --var DB_PORT=5432 \
  --set generators[0].options.dialect=sqlite
```

### 7.2. Флаги

| Флаг                        | Описание                                         |
|-----------------------------|--------------------------------------------------|
| `--config`, `-c`            | Путь к метакогфигу (по умолчанию `.mg.yaml`)     |
| `--generator`, `-g`         | Список генераторов через запятую                |
| `--output`, `-o`            | Корневая директория для артефактов              |
| `--var KEY=VALUE`           | Переменные окружения для подстановки в шаблоны  |
| `--set`                     | Переопределение параметров генератора            |
| `--watch`, `-w`             | Режим наблюдения за изменениями файлов           |
| `--dry-run`                 | Показать результат без записи файлов             |
| `--format`                  | Формат вывода CLI: `text` (default) или `json`  |
| `--verbose`, `-v`           | Подробный вывод                                  |
| `--quiet`, `-q`             | Только ошибки                                    |

## 8. Валидация

### 8.1. Валидация исходной модели

Валидация выполняется **до** генерации и включает:

| Проверка                                | Серьёзность    |
|-----------------------------------------|----------------|
| Синтаксис YAML                          | Error          |
| Корректность типов данных               | Error          |
| Ссылки на несуществующие сущности в relations | Error    |
| Ссылки на несуществующие enum/type       | Error          |
| Дублирующиеся имена сущностей/полей     | Error          |
| Корректность regex в constraints.pattern | Error         |
| Пустые обязательные поля                | Warning        |
| Неиспользуемые enum/type                | Warning        |
| Потенциально небезопасные default-значения | Warning      |

### 8.2. Валидация результатов генерации

Каждый генератор может (и должен) валидировать свой вывод:

- **SQL-генераторы** — результат парсится обратно, проверяется синтаксис
- **TypeScript-генератор** — результат проверяется через `tsc --noEmit`
- **Python-генераторы** — результат проверяется через `mypy` / `pyright`
- **JSON Schema** — валидация через `jsonschema` library

Ошибки валидации выводятся, но **не блокируют** генерацию (с флагом `--force`).

## 10. Требования к качеству

### 10.1. Тестовое покрытие

- Минимум **80%** покрытия кода тестами
- Тесты на все встроенные генераторы (golden tests — сравнение с эталонным выводом)
- Property-based тесты через `hypothesis` для парсинга моделей
- Интеграционные тесты: полный цикл YAML → артефакт → валидация

### 10.2. Производительность

- Парсинг модели < 50 мс для файла до 1000 сущностей
- Генерация одного артефакта < 100 мс
- Суммарное время генерации всех встроенных генераторов < 5 секунд для модели из 50 сущностей

### 10.3. Документация

- Обязательно: README с примером использования
- Обязательно: примеры моделей (fixtures) для каждого генератора
- Обязательно: документация по формату модели и метакогфига
- Обязательно: руководство по созданию собственного генератора-плагина

## 11. Расширяемость

### 11.1. Создание собственного генератора

Пользователь создаёт Python-пакет:

```python
# my_generator/__init__.py
from metadata_generator.generators.base import BaseGeneratorPlugin, GenerationResult, Artifact

class MyCustomGenerator(BaseGeneratorPlugin):
    @property
    def id(self) -> str:
        return "my-custom-generator"

    @property
    def name(self) -> str:
        return "My Custom Generator"

    def generate(self, model, config, context) -> GenerationResult:
        # ... логика генерации ...
        return GenerationResult(artifacts=[
            Artifact(path="output.json", content="...", mime_type="application/json")
        ])
```

Регистрация в `pyproject.toml`:

```toml
[project.entry-points."metadata_generator.generators"]
my-custom-generator = "my_generator:MyCustomGenerator"
```

После установки пакета генератор доступен через CLI.

### 11.2. Хуки (pre/post generation)

```python
# hooks/my_hooks.py
def pre_python_hook(entity, context):
    print(f"Generating {entity.name}...")

def post_python_hook(artifacts, context):
    for artifact in artifacts:
        print(f"Created: {artifact.path}")
```

Хуки подключаются через метакогфиг:

```yaml
generators:
  - id: my-oracle-generator
    hooks:
      pre: my_hooks.pre_oracle
      post: my_hooks.post_oracle
```

## 13. Пример end-to-end

### 13.1. Входной файл: `model.yaml`

```yaml
format: entity-model
version: "1.0"
updated_at: "2025-11-03"
model:
  name: blog-platform
  entities:
    - name: User
      description: Пользователь блога
      fields:
        - name: id
          type: uuid
          required: true
        - name: email
          type: string
          required: true
        - name: username
          type: string
          required: true
          constraints:
            min_length: 3
            max_length: 50
        - name: created_at
          type: datetime
          required: true
          default: now()

    - name: Post
      description: Статья блога
      fields:
        - name: id
          type: uuid
          required: true
          primary_key: true
        - name: title
          type: string
          required: true
          constraints:
            min_length: 1
            max_length: 255
        - name: content
          type: text
          nullable: true
        - name: author_id
          type: uuid
          required: true
        - name: published_at
          type: datetime
          nullable: true
        - name: status
          type: PostStatus   # ссылка на enum
          required: true
          default: draft

  enums:
    - name: PostStatus
      values:
        - name: draft
          value: draft
        - name: published
          value: published
        - name: archived
          value: archived
```

### 13.2. Метакогфиг: `.mg.yaml`

```yaml
version: "1.0"

defaults:
  naming_convention: snake_case

sources:
  - path: ./model.yaml
    entities: [User, Post]        # Берём все сущности
    enums: [PostStatus]           # И enum

generators:
  - id: oracle-ddl                # Генератор под конкретный проект
    enabled: true
    input:
      entities: [User, Post]
    output_dir: ./output/oracle
    options:
      tablespace: USERS

  - id: snowflake-schema
    enabled: true
    input:
      entities: [User, Post]
    output_dir: ./output/snowflake
    options:
      warehouse: COMPUTE_WH
```
