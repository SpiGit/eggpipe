# Метаинформационный генератор — Техническое задание v1.1

## 1. Цель и назначение

**Назначение:** инструмент командной строки (CLI), который читает описание модели данных из файла формата YAML и порождает из него артефакты в произвольных целевых форматах (SQL-миграции, JSON-схемы, YAML-конфиги, Python-модели, TypeScript-типы и т.п.).

**Ключевая философия:** один источник истины — YAML-описание модели — и произвольное количество генераторов-«адаптеров», каждый из которых умеет превращать одну и ту же модель в свой формат.

**Ключевые свойства ядра:**

- Ядро **не содержит генераторов** — все генераторы это плагины, подключаемые через entry points.
- Ядро содержит **ровно один встроенный формат** `entity-model` (базовый, формат-нейтральный). Остальные форматы (sql-model, ts-model, и т.п.) регистрируются **плагинами форматов**.
- Сущности в модели **изолированы**: ядро не знает о связях между сущностями (relations). Если связь нужна — она описывается отдельной сущностью или механикой конкретного формата в плагине.
- Все нетривиальные правила (типы, связи, naming, шаблоны) относятся к плагинам; ядро обеспечивает только парсинг, композицию, валидацию базового формата, оркестрацию и запись артефактов.

**Целевая аудитория:** fullstack-команды, разработчики API-first сервисов, инженеры, которым нужна консистентность между схемой БД, спецификацией API и клиентскими типами.

## 2. Термины

| Термин | Определение |
|--------|-------------|
| **Документ модели** | YAML-файл с заголовком (`format`, `version`) и секцией `model` |
| **Исходная модель** | Секция `model` — сущности (`entities`), перечисления (`enums`), пользовательские типы (`types`) |
| **Формат** | Зарегистрированный тип документа. Определяет **парсер** и правила валидации. Базовый формат `entity-model` встроен в ядро; остальные форматы регистрируются плагинами |
| **Формат-плагин** | Плагин, регистрирующий формат (parser + валидация формата) |
| **Генератор** | Плагин, преобразующий модель (или её срез) в целевой формат |
| **Шаблон** | Шаблон (формат зависит от генератора), используемый для рендеринга |
| **Артефакт** | Результат генерации: один файл, у которого есть path и content |
| **Метаконфиг** | `.mg.yaml` — источники, генераторы, переменные, defaults |
| **Манифест вывода** | Файл в `output_dir`, в котором ядро фиксирует артефакты текущего запуска (для cleanup) |

## 3. Формат исходной модели (YAML)

### 3.1. Структура документа

```yaml
# === Заголовок документа (обязательные поля) ===
format: entity-model     # имя зарегистрированного формата
version: "1.0"           # версия СХЕМЫ ФОРМАТА (не модели!)

# === Описание модели ===
model:
  name: string
  description: string

  imports:                                 # импорты (см. 3.5)
    - path: ./shared/audit-fields.yaml     # YAML-модель: merge, композиция
    - path: ./icons/user.svg
      as: avatar_icon                      # произвольный файл: доступен по имени

  entities:
    - name: User
      description: string
      version: "1"                         # опционально: версия сущности
      updated_at: 2026-11-10               # опционально: дата изменения сущности (ISO 8601)
      extends: ./audit-fields              # опционально: entity-level наследование полей
      fields:
        - name: string                    # имя поля
          type: string                    # примитив или ссылка на enum/type
          description: string
          required: boolean               # default: false
          nullable: boolean               # default: false (см. 3.6)
          default: string | number | boolean | null   # скаляр (см. 3.7)

  enums:
    - name: string
      description: string
      values:
        - name: string
          value: string | number          # опционально (default = name)
          description: string

  types:                                  # пользовательские алиасы
    - name: string
      base: string                        # базовый примитив
      constraints:
        min: number
        max: number
        min_length: number
        max_length: number
        pattern: string
```

**Изменения относительно v1.0:**

| Было | Стало | Причина |
|------|-------|---------|
| `extends: base` в заголовке документа | Поле удалено | Наследование формата задаёт сам формат-плагин; "двойное наследование" в заголовке противоречиво |
| `updated_at` (и `version`) в заголовке | Перенесены на уровень **entity** | Поле должно трекать изменение именно сущности |
| `default: auto` в `Field.default` | Удалено из базовой схемы | `auto` — инструкция исполнителю, не значение. База нейтральна: автогенерация описывается на уровне формата/генератора |
| `nullable` упомянут только в примере | Явно в схеме с `default: false` | Согласована null-семантика (3.6) |
| `import` доступ как `entity.imports[...]` | Модель-level `model.imports` → доступ через `GenerationContext.imports` | Импорты ресурсов — уровень модели, не entity |

### 3.2. Примитивные типы

| Тип | Описание |
|-----|----------|
| `string` | Строка |
| `text` | Длинный текст |
| `integer` | Целое число |
| `bigint` | Большое целое |
| `boolean` | Логический тип |
| `float` | Число с плавающей точкой |
| `date` | Дата |
| `datetime` | Дата и время |
| `uuid` | UUID |
| `json` | JSON-объект |

Это набор встроенного формата `entity-model`. Пользовательский формат (через плагин формата) может добавлять/переопределять собственные типы (`serial`, `decimal`, `inet` для SQL и т.п.).

### 3.3. Правила разрешения типов

- Тип, совпадающий с именем `enum` или `type` из модели (после композиции), раскрывается в их определение.
- Неизвестный тип → **Error** валидации.

### 3.4. Форматы документа

- Заголовок содержит только `format` и `version`. Больше ничего.
- `format` = ключ в **реестре форматов** (FormatRegistry). Этот формат парсит документ.
- **Базовый формат `entity-model` встроен**, формат-нейтральный: он умеет ровно то, что описано в 3.1.
- **Пользовательские форматы** регистрируются формат-плагинами через entry points (группа `metadata_generator.formats`). Формат-плагин определяет:
  - имена поддерживаемых форматов (`sql-model`, `ts-model`...);
  - поддерживаемые версии (`version`), несовместимая версия → понятная ошибка (не "тихое" поведение);
  - дополнительные поля схемы (relations — если само решит, `column.generated` для `auto`-семантики, naming-стиль БД, etc.);
  - собственную валидацию.
- Формат-плагин наследует поведение базового формата (расширяет, а не заменяет). Как именно — деталь реализации формат-плагина (см. System Design).

### 3.5. Композиция (Composition)

#### 3.5.1. Варианты хранения сущностей

**Вариант 1: Monolith (всё в одном файле)**
```
model.yaml           # все entities, enums, types
```

**Вариант 2: File-per-entity**
```
entities/
  user.yaml
  post.yaml
common/
  enums.yaml
  types.yaml
```

**Вариант 3: Directory-per-entity**
```
entities/
  user/
    model.yaml       # entity: User
    avatar.svg       # ресурсы для генерации
    description.md
```

Во всех вариантах итоговая модель собирается по правилам `sources` метаконфига (§5): каждый файл — самостоятельный документ модели; результат — их объединение. - ~"Лишние" (только для композиционного сложения) файлы объявляются явно через `sources`/`imports`.~ Дополнительные файлы моделей подключаются явно через `sources`/`imports`.

#### 3.5.2. Imports

Два типа:

**A. YAML-модели** (композиция/наследование):
```yaml
format: entity-model
version: "1.0"
model:
  imports:
    - path: ./base-entity.yaml
    - path: ../shared/audit-fields.yaml
  entities:
    - name: Post
      extends: ./audit-fields     # наследование полей от импортированного
      fields:
        - name: title
          type: string
```
YAML-импорты **мержатся** в модель по правилам ADR-0001. Импортированные документы также валидируются как модели.

**B. Произвольные файлы** (ресурсы для генерации):
```yaml
model:
  imports:
    - path: ./icons/user.svg
      as: avatar_icon
    - path: ./templates/card.html
      as: card_template
```
Произвольные импорты доступны плагину в `GenerationContext.imports` под именем `as` (как текст или bytes). Содержимое файлов не парсится ядром.

#### 3.5.3. Правила

- Пути разрешаются относительно файла, где объявлен импорт (`./`, `../` только; абсолютные пути — ошибка).
- Импорты транзитивны (из родительских файлов наследуются).
- Циклические импорты — **Error** (полный путь в сообщении: `a.yaml → b.yaml → a.yaml`).
- Глубина импортов ≤ 10 (защита от бесконечной рекурсии).
- Совпадения имён (entities/enums/types) между несвязанными файлами — **Error**.
- Полная семантика merge — **[ADR-0001](../adr/0001-composition-merge-semantics.md)** (источник истины по правилам слияния).

#### 3.5.4. Entity-level extends

```yaml
entities:
  - name: Post                   # в main.yaml
    extends: ./shared/audit      # из импортированного документа
    fields:
      - name: title
        type: string
```
Правила merge полей: parent-поля — на своих позициях; поле с тем же `name` в child **полностью замещает** родительские атрибуты; новые поля child — в конце. Только `fields` — без описаний/метаданных.

### 3.6. Null-семантика

Три независимых измерения поля:

- `required` — значение **обязательно при создании** сущности; отсутствие = ошибка валидации (на уровне модели приложения, не генерации).
- `nullable` — если значение предоставлено, оно может быть `null`. **Default: `false`** (по умолчанию поле непустое).
- `default` — значение, подставляемое, когда поле не указано при создании.

| required | nullable | default | Смысл |
|:--------:|:--------:|:-------:|-------|
| `true`  | `false` | — | Обязательное непустое поле |
| `true`  | `false` | ✓ | Обязательное, но может не указываться при создании (default) |
| `false` | `true`  | — | Полностью опциональное (может отсутствовать или быть null) |
| `false` | `false` | ✓ | Всегда есть значение: либо указано, либо default |

**Запрещённые комбинации:**

| Комбинация | Серьёзность |
|------------|-------------|
| `required=false, nullable=false, default=отсутствует/null` | **Error** — поле невозможно ни пропустить, ни заполнить |
| `required=true` и `nullable=true` одновременно | **Warning** — противоречивое описание (легитимно только для PATCH-семантики, которой в v1 нет) |
| `required=true` и `default=null` | **Error** |

Nullable и constraints касаются **поля**, не типа, на который оно ссылается (`CustomType` не переносит `nullable` самостоятельно).

### 3.7. Default (без `auto`)

- `default` — **скалярное значение**: `string | number | boolean | null`. Никаких `auto`/`generated`/`serial` в базовой схеме.
- Автогенерация (`uuid4` на вставке, `created_at=now()`, `identity`-колонка, `nextval`) — ответственнность конкретного **формата/генератора**: например, формат-плагин `sql-model` добавит собственное поле вида `column: {generated: identity}`.

## 4. Принцип «данные отделимы от генерации»

Ключевая идея: **модель — это просто данные**. Нет жёсткой привязки «тип модели» → «генераторы».

Пользователь описывает данные один раз, а в метаконфиге решает:
- Какие сущности взять из модели.
- Какие генераторы применить.
- Какие enum'ы и типы включить.
- Какие `variables` передать генераторам.

Один и тот же набор сущностей может порождать разные артефакты в разных генераторах.

## 5. Метаконфиг `.mg.yaml`

```yaml
version: "1.0"

defaults:
  naming_convention: snake_case   # подсказка плагинам: ядро НЕ переименовывает модель
  required_by_default: false

variables:                        # переменные, доступные плагинам через context.vars
  env: dev

sources:
  - path: ./models/main.yaml      # файл или каталог
    entities: []                  # пусто = все
    enums: []
    types: []

generators:
  - id: oracle-ddl
    enabled: true
    input:
      entities: [User, Post]      # срез для этого генератора
      enums: [PostStatus]
    output_dir: ./output/oracle
    on_conflict: overwrite        # overwrite | skip | error
    cleanup: prompt               # off | prompt | enabled (см. §10)
    options: {}                   # произвольные опции плагина (в т.ч. file_naming — зона плагина)
```

**Semantics срезов:** финальный срез генератора = пересечение `sources.entities/enums/types` (пусто = все) и `generators[].input.entities/enums/types` (пусто = все). У генератора **нет поля `source`** — он работает с составленной срезом моделью целиком.

### 5.1. Подключение

Каждый генератор — **плагин**:
- Уникальный `id`.
- Реализует контракт `GeneratorPlugin` (§6, детали в System Design).
- Подключается через entry points (группа `metadata_generator.generators`).
- Получает данные через `sources` + `input`.
- Проверяет `api_version` при загрузке (§6.2).

## 6. Контракты плагинов

### 6.1 GeneratorPlugin (генератор)

```python
class GeneratorPlugin(ABC):
    api_version: Literal["1"]      # версия контракта; ядро проверяет
    id: str                        # должен совпадать с entry point id
    name: str                      # человекочитаемое имя

    def generate(self, input: GeneratorInput) -> GenerationResult: ...
    def validate_config(self, config: GeneratorConfig) -> list[str]: ...
```

**Вход** (`GeneratorInput`): *целиком* составленный и отфильтрованный (по срезу) `SourceModel`, `GenerationContext` (vars, имя-конвенция-подсказка, импортированные файлы, путь источника) и `GeneratorConfig` из `.mg.yaml`. **AppConfig (технические настройки) плагину не передаётся.**

**Выход** (`GenerationResult`): список `Artifact`; каждый артефакт содержит **относительный путь** (`path`) и `content` (text, encoding utf-8). Финальный путь = `output_dir` + `artifact.path`. Имена файлов — зона плагина; ядро выполняет только проверку нормализации и границ.

### 6.2 Versioning plugin API

- `api_version` плагина проверяется ядром при загрузке.
- Несовпадение → понятная ошибка ("plugins oracle-ddl требует metadata-generator>=X").
- Публичный API ядра (`metadata_generator.__init__`) экспортирует стабильно только контрактные сущности: `GeneratorPlugin, GeneratorInput, GenerationResult, Artifact, GenerationContext, SourceModel, Entity, Field, Enum, CustomType`. Всё остальное (`core.*`) — внутренняя реализация и может меняться.

### 6.3 FormatPlugin (формат)

Плагин формата регистрирует новый формат (пример `sql-model`) в реестре:
- Имя формата (совпадает с `format` в заголовке документа).
- Поддерживаемые версии схемы (несовпадение `version` → понятная ошибка).
- Дополнительные поля схемы и собственная валидация поверх базовой.
- Автоматически получает базовое поведение entity-model (сущности изолированы, merge композиции, null-matrix) и может его расширять.

## 7. Шаблонизация

Механизм шаблонов — зона генератора. Ядро передаёт:
- Распарсенную модель (SourceModel).
- `GenerationContext` (vars, imports, naming hint).
- `GeneratorConfig` (в том числе пути templates от пользователя).

Каждый генератор может:
- Использовать свой движок (Jinja2, Mako, etc).
- Поставлять шаблоны внутри себя.
- Позволять пользователю переопределять шаблоны (паттерн согласуется плагином через `options`).

## 8. CLI

### 8.1. Команды (единый подкомандный стиль)

```bash
# Генерация
mg generate                                                  # все sources, все генераторы
mg generate ./models/blog.yaml                               # одна модель, все генераторы
mg generate ./models/blog.yaml -g oracle-ddl                 # конкретные генераторы
mg generate ./models/blog.yaml ./models/users.yaml -g oracle-ddl
mg generate -g oracle-ddl                                    # все sources, конкретные генераторы

# Watch (dev-режим)
mg watch                                                     # все
mg watch ./models/blog.yaml                                  # конкретная модель

# Конфигурация
mg init
mg config show
mg config validate

# Модели
mg model validate ./models/blog.yaml

# Плагины
mg gen list
```

### 8.2. Флаги

| Флаг | Описание |
|------|----------|
| `--config, -c` | Путь к метаконфигу (default: `.mg.yaml`) |
| `--generator, -g` | Список генераторов (запятая или повторяющиеся флаги) |
| `--output, -o` | Корневая директория для артефактов |
| `--var KEY=VALUE` | Переменные для плагинов (см. 8.3) |
| `--dry-run` | Показать результат без записи файлов |
| `--format` | Вывод CLI: `text` (default) | `json` |
| `--strict` | Treat warnings as errors |
| `--verbose, -v` | Подробный вывод |
| `--quiet, -q` | Только ошибки |

### 8.3. Переменные (`--var`)

- Источники: `--var KEY=VALUE` (CLI) и `variables:` в `.mg.yaml`.
- Приоритет: **CLI > `.mg.yaml`**.
- Ядро собирает `context.vars: dict[str, str]` и передаёт всем плагинам в `GenerationContext`.
- Ядро **никогда не применяет vars молча** — как именно их использовать в форматах/именах/шаблонах, решает плагин.

### 8.4. Выходные коды и поведение при ошибках

- Если один генератор упал — **остальные продолжаются**.
- Exit code `0` — успех; `1` — были errors при генерации (в т.ч. --strict warnings); `2` — config/usage error (некорректные флаги, недоступный `.mg.yaml`, нагрузка плагина).

## 9. Валидация

### 9.1. Исходная модель

| Проверка | Серьёзность |
|----------|-------------|
| Синтаксис YAML | Error |
| Корректность типов (`type` из известного набора или ссылка на enum/type) | Error |
| Ссылка на несуществующий enum/type | Error |
| Ссылка `entity.extends` на несуществующий импорт | Error |
| Дубликаты имён (entity/enum/type) после композиции | Error |
| Дубликат имени поля в entity | Error |
| Корректность regex в `constraints.pattern` | Error |
| Поле name pattern (`^[a-zA-Z_][a-zA-Z0-9_]*$`) | Error |
| Null-matrix запрещённые комбинации (§3.6) | Error |
| Циклические импорты / глубина > 10 | Error |
| Поля `default`, не приводящиеся к `type` | Warning |
| `required=true` + `nullable=true` | Warning |
| Entity name не в PascalCase | Warning |
| Неиспользуемый enum/type | Warning |
| Пустой `description` у обязательного поля | Warning |
| `updated_at` у entity старше mtime файла | Warning ("модель менялась, дата — нет") |
| Потенциально небезопасное `default` (для string: SQL-инъекции, скрипты) | Warning |

Валидация выполняется **до** генерации. `--strict` повышает warnings до errors.

### 9.2. Валидация результатов генерации

Каждый генератор отвечает за валидацию своего вывода. Ядро выполняет **свои** проверки только структурные:
- `artifact.path` нормализованный, не выходит за границы `output_dir` (Error) 
- `content` — строка (Error валидации контракта плагина).

Ошибка одного генератора **не отменяет** других (см. §8.4).

## 10. Запись артефактов

- **Финальный путь** = `output_dir` + `Artifact.path` (POSIX-путь, нормализованный). Выход за пределы `output_dir` → Error.
- **on_conflict** (настройка генератора в `.mg.yaml`):
  - `overwrite` — по умолчанию, перезаписать.
  - `skip` — не трогать существующий файл (для повторных прогонов поверх ручных изменений).
  - `error` — прервать генератор с ошибкой.
- **Atomicity:** запись сначала в staging временный каталог, потом атомарно move в `output_dir`. При падении середины — не остаётся полу-записанных артефактов.
- **Манифест:** ядро после успешного полного запуска пишет `.mg-manifest.json` в `output_dir` со списком записанных файлов.
- **Cleanup:** файлы в `output_dir`, отсутствующие в манифесте, — кандидаты на удаление ("осиротевшие"). Политика `cleanup`:
  - `off` — не трогать;
  - `prompt` — интерактивно спрашивать (если stdout не tty — fallback `off` с предупреждением);
  - `enabled` — удалить.
  Разовый запуск поверх текущей настройки: `mg generate --clean` / `mg clean`. **Cleanup работает только по манифесту**, никогда не по "незафиксированным" файлам.

## 11. Архитектура

Две независимые части: **ядро** и **плагины**.

### 11.1. Ядро (metadata-generator)

```
metadata-generator/
├── src/metadata_generator/
│   ├── __init__.py                 # публичный API (стабильный)
│   ├── cli/
│   │   ├── main.py                 # typer app, entry point
│   │   ├── generate.py
│   │   ├── watch.py
│   │   ├── config_cmds.py
│   │   ├── model_cmds.py
│   │   └── gen_cmds.py
│   ├── core/
│   │   ├── model.py                # Pydantic-модели: SourceModel, Entity, Field, ...
│   │   ├── parser.py               # YAML parse, imports/extends
│   │   ├── composition.py          # merge по ADR-0001
│   │   ├── validator.py            # cross-entity semantic checks (warnings+errors)
│   │   └── naming.py               # NamingStyle + transform()

│   │   ├── engine.py               # orchestration
│   │   ├── plugin_loader.py        # entry points (generators + formats)
│   │   ├── format_registry.py      # реестр форматов

├── tests/                          # unit, property, integration, golden
├── docs/
├── pyproject.toml

```

**Ядро содержит:** CLI, парсинг (встроенный формат `entity-model`), композицию (merge по ADR-0001), валидацию, оркестрацию, запись артефактов, загрузку плагинов (entry points), naming-утилиты, логирование.

**Ядро НЕ содержит:** генераторов, шаблонов, моделей связей (relations), форматов вне встроенного `entity-model`.

### 11.2. Плагин

Каждый генератор — отдельный Python-пакет. Содержит логику генерации + шаблоны (+ опционально свой формат, если это format-плагин).

```
my-oracle-generator/
├── pyproject.toml                     # entry points
├── src/my_oracle_generator/
│   ├── __init__.py                    # MyGenerator(GeneratorPlugin)
│   ├── renderer.py
│   └── templates/
│       └── entity.sql.j2
├── tests/
└── README.md
```

Регистрация:

```toml
[project.entry-points."metadata_generator.generators"]
oracle-ddl = "my_oracle_generator:MyGenerator"

# при необходимости:
[project.entry-points."metadata_generator.formats"]
sql-model = "my_oracle_generator.format:SqlModelFormat"
```

### 11.3. Поток данных

```
CLI → AppConfig → GeneratorRules (.mg.yaml)
                        │
        ┌───────────────┼────────────────┐
        ▼               ▼                ▼
   Parser (FormatRegistry) → Composition (ADR-0001) → Validator → [SourceModel срез]
                                                                      │
                                          Plugin Loader (entry points, api_version)
                                                                      │
                                              для каждого генератора:
                                              generate(GeneratorInput) → GenerationResult
                                                                      │
                                              Artifact Writer (path validation,
                                                                   on_conflict, atomic, manifest)
                                                                      │
                                              CLI Output (text / json)
```

### 11.4. Стек технологий

| Компонент | Технология |
|-----------|------------|
| CLI | Typer |

| Watch | watchdog (lazy-import для mg watch) |
| Вывод | Rich |

| Линтер | ruff + mypy |

### 11.5. Конфигурация

#### 11.5.1. Application Config (технический)

Логирование, пути, debug; источники приоритета:
1. Environment vars (`MG_LOG_LEVEL`, etc.)
2. `.env`
3. Config file
4. Defaults

> Детали — System Design §5.

#### 11.5.2. Generator Rules (`.mg.yaml`)

Бизнес конфигурация: sources, generators, variables, defaults (см. §5). Слово "Config" в нейминге бизнес-классов не используется (`GeneratorRules`, `GeneratorRulesLoader`, файл `config/generator_rules.py`).

### 11.6. Локальная разработка плагина

`sys.path`-хаки и загрузчик "плагинов из директории" **не поддерживаются**. Дев-цикл:

```bash
pip install -e ./plugins/my-generator    # или uv editable install
mg gen list                              # плагин виден
```

(Future опция: `--plugin path/to/module.py` через явный importlib-spec-loading без правки `sys.path`.)

## 12. Требования к качеству

### 12.1. Тесты

- ≥ 80% покрытия ядра.
- Property-based (hypothesis): parser не падает на произвольном dict; round-trip `SourceModel → dict → SourceModel` консистентен; strategy строит валидные и невалидные модели (в валидных — все проверки проходят, в невалидных — ровно ожидаемая ошибка).
- Integration: полный цикл CLI → config → parse → composition → generate → запись.
- **Golden-file тесты**: фикстуры моделей → ожидаемые артефакты (для RDiff-регрессии артефактов).
- Merge-семантика (ADR-0001) — собственный набор тестов на каждое правило (1–12).

### 12.2. Производительность

- Парсинг модели < 50 мс на файл до 1000 сущностей.
- Генерация до передачи плагину < 100 мс (без учёта самого генератора).

### 12.3. Документация

- README с примером использования.
- Фикстуры моделей для каждого генератора.
- Документация формата модели и метаконфига.
- Руководство по созданию generator-плагина.
- **ADR-практика** (`docs/adr/`) для решений уровня merge/contract (см. ADR-0001).

## 15. Пример end-to-end

### 15.1. Модель: `model.yaml`

```yaml
format: entity-model
version: "1.0"

model:
  name: blog-platform
  entities:
    - name: User
      version: "1"
      updated_at: 2026-11-10
      fields:
        - {name: id, type: uuid, required: true}
        - {name: email, type: string, required: true}
        - name: username
          type: string
          required: true
          constraints:
            min_length: 3
            max_length: 50
        - {name: created_at, type: datetime, required: true, nullable: false}
        - {name: bio, type: text, nullable: true}          # optional + nullable

    - name: Post
      fields:
        - {name: id, type: uuid, required: true}
        - name: title
          type: string
          required: true
          constraints: {min_length: 1, max_length: 255}
        - {name: content, type: text, nullable: true}
        - {name: status, type: PostStatus, required: true, default: draft}
        # SQL-специфика (identity, generated created_at) — semantic плагина sql-model

  enums:
    - name: PostStatus
      values:
        - name: draft
        - name: published
        - name: archived

  types:
    - name: MediumText
      base: text
      constraints: {max_length: 5000}
```

### 15.2. Метаконфиг: `.mg.yaml`

```yaml
version: "1.0"

defaults:
  naming_convention: snake_case

variables:
  env: dev

sources:
  - path: ./model.yaml

generators:
  - id: oracle-ddl
    enabled: true
    input:
      entities: [User, Post]
      enums: [PostStatus]
    output_dir: ./output/oracle
    on_conflict: overwrite
    cleanup: prompt
    options:
      tablespace: USERS

  - id: ts-types
    enabled: true
    input:
      entities: [User, Post]
    output_dir: ./output/ts
```

### 15.3. Запуск

```bash
$ mg generate

[✓] Validating (0 errors, 0 warnings)
[✓] oracle-ddl → ./output/oracle/  (2 files)
[✓] ts-types → ./output/ts/       (1 file)

2 generators, 3 files, 0 warnings, 0 errors
```
