# Roadmap Eggpipe

- **Статус:** рабочая версия
- **Дата:** 2026-11-17
- **Текущий релиз:** `0.3.2` (beta); следующий — `0.4.0`
- **Связанные документы:** [План v2.0](./plan-v2.md), [ADR-0014](./adr/0014-beta-status-and-compatibility.md), [Релиз](./release.md)

## 1. Контекст

Релиз `0.3.2` опубликован на PyPI, документация доступна на
https://spigit.github.io/eggpipe/, `main` защищён и изменения идут через pull request.

До `1.0` проект остаётся beta: публичный API, CLI, конфиг и генерируемые артефакты
могут меняться. Главная задача следующего этапа — не добавлять всё подряд, а сделать
ядро предсказуемым, плагины удобными, а релизы регулярными.

### 1.1. Текущая точка (2026-11-17)

- `main`: `99c425b`; актуальное ТЗ — v2.4 (per-entity generation).
- Готово: incremental generation (ADR-0017, #18), per-entity generation (ADR-0018, #32/#33), PR-процесс и backlog (#19–#31).
- Открыто в backlog: B-023 (tests/coverage в PR body), B-024 (тесты merge manifest).
- Следующее: аудит инженерной документации, затем watch improvement.

## 2. Принципы

- Сначала ТЗ и ADR, потом код. Контракты не меняются задним числом.
- Патч-релизы — только исправления; breaking changes — в minor до `1.0`.
- Один PR — одна логическая задача; `main` обновляется только через PR.
- Приоритет — реальные пользовательские сценарии: генерация, плагины, диагностика.
- Документация и примеры обновляются вместе с кодом.
- После `1.0` — обычный SemVer: breaking changes только в major.

## 3. Направления развития

| Направление | Цель | Почему сейчас |
|-------------|------|---------------|
| Стабилизация и 1.0 | Зафиксировать публичный API и политику совместимости | Пора готовить `1.0`, пока аудитория небольшая |
| Ядро генерации | Надёжность, скорость, инкрементальность | Основная ценность продукта |
| Плагины | Удобный старт и контрактные тесты | Без экосистемы плагинов инструмент остаётся демо |
| Документация и UX | Понятный путь от установки до своего плагина | Снижает порог входа |
| Качество и безопасность | Регрессии, supply chain, бенчмарки | Нужно для доверия и `1.0` |
| Бренд и сообщество | Узнаваемость и обратная связь | Помогает развитию после релиза |

## 4. Вехи

### 0.4.0 — Plugin DX

Фокус: сделать написание плагинов быстрым и предсказуемым.

- шаблон плагина (`cookiecutter`/`uv`-template) с генератором и форматом;
- набор contract-тестов для авторов плагинов;
- примеры: SQL, Pydantic, TypeScript, OpenAPI;
- улучшение `eggpipe gen info` и `eggpipe format info`;
- понятные ошибки контракта плагина;
- раздел «Первый плагин за 10 минут» в документации.

### 0.5.0 — Reliability

Фокус: скорость и устойчивость генерации.

- L1-инкрементальная генерация по manifest-хешам — сделано (ADR-0017);
- кэш разбора и композиции (L2/L3);
- `generate` для одной сущности/модели — сделано (#32/#33);
- улучшение watch: батчинг, отмена устаревших запусков;
- авто-discovery ресурсов (если подтвердится сценарием);
- бенчмарки на TPC-H и синтетических моделях.

### 0.6.0 — 1.0 readiness

Фокус: заморозка контрактов.

- аудит публичного API и `__all__`;
- политика deprecation и окно поддержки;
- compatibility-тесты для плагинов и форматов;
- migration guide для пользователей `0.x`;
- финальный аудит документации и примеров;
- проверка wheel/sdist, attestations и release workflow.

### 1.0.0

Критерии:

- публичный API и CLI зафиксированы;
- есть политика совместимости и deprecation;
- плагины имеют стабильный контракт и тестовый набор;
- документация покрывает установку, CLI, API, плагины и диагностику;
- CI зелёный на поддерживаемых Python/OS;
- релизный процесс воспроизводим без ручных шагов, кроме тега.

### Reference examples

- SQL/Pydantic — пока только внутри TPC-H как часть бенчмарка; вынос в общий
  переиспользуемый reference-плагин — отдельная задача.
- TypeScript/OpenAPI — следующие кандидаты.
- PostgreSQL transform/upsert — кандидат в `0.5.0`:
  - формат-плагин, наследник `entity-model`; имя формата и namespace выбирает плагин;
  - в примере используется namespace `metadata.transform`;
  - одна upsert-процедура на сущность;
  - field mapping/cast, без joins между сущностями;
  - явная пометка «example, не поддерживаемый продукт».

Не входит в scope примеров: dbt, ETL-оркестрация, scheduling, lineage.
Relations в ядре остаются открытым вопросом 2.

## 6. Релизный ритм

- Патчи — по мере необходимости, без breaking changes.
- Minor — примерно раз в 4–6 недель, с одной крупной темой.
- Перед релизом: PR → зелёный `ci-success` → merge → тег с `main`.
- `CHANGELOG.md` обновляется в том же PR, что и изменение.
- После `1.0` — релизы по SemVer, breaking changes только в major.
