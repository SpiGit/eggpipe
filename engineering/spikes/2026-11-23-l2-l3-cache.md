# Spike: L2/L3 кэш разбора и композиции

- **Дата:** 2026-11-23
- **Статус:** завершён; рекомендация — отдельный ADR-0020 и реализация L2 в 0.5.0
- **Связанные документы:** [Roadmap §0.5.0, п. 2](../roadmap.md), [ADR-0017](../adr/0017-incremental-generation.md), [System Design §8.6, §9.3](../system-design/index.md), [ТЗ v2.4 §10.7](../requirements/v2.4.md), [Benchmarks](../benchmarks.md)

## 1. Вопрос

Пункт 2 roadmap 0.5.0: «кэш L2/L3: разбор и композиция по fingerprint — повторный
запуск не парсит неизменённые файлы». Нужно понять до реализации:

1. где именно уходит время в повторном прогоне и в сценарии «изменён один из N файлов»;
2. какую долю этого времени реально снимает кэш разбора (L2) и кэш композиции (L3);
3. достаточно ли зарезервированного интерфейса `CacheStrategy` (System Design §9.3);
4. стоит ли L2/L3 отдельного усложнения состояния до 1.0.

Границы: spike не меняет код, ТЗ и ADR. Результат — замеры и рекомендация.

## 2. Текущее поведение

`--incremental` (ADR-0017, L1) работает на уровне location: discovery → fingerprint →
сверка manifest. При совпадении всего прогон завершается без parse/validate/generate.
Если изменился хотя бы один файл, выполняется полный путь: discovery, fingerprint,
parse + composition, validation, генераторы, запись.

Ключевая деталь: discovery и fingerprint **сами по себе** полностью разбирают YAML всех
source-документов, даже при cache-hit:

- `discovery._is_model_document` вызывает `load_yaml(path)` только чтобы проверить
  наличие ключа `format` (`core/discovery.py:534`);
- `Engine._fingerprint_files` повторно разбирает каждый YAML, чтобы получить `imports`
  через `FormatPlugin.input_paths` (`engine/engine.py:488`).

Итого в incremental-прогоне каждый документ разбирается 2 раза (no-op) или 3 раза
(изменён один файл: discovery + fingerprint + `Parser.parse_document`).

## 3. Методика

- Python 3.11.18, Linux (WSL2), 12 CPU; коммит `e4ad9ee`.
- Медианы по 9 итерациям, прогрев 2 итерации; между итерациями manifest возвращался
  в актуальное состояние, чтобы cache-hit не искажался предыдущей мутацией.
- TPC-H (`examples/tpc-h`, 8 документов, 10 230 байт) с реальным `tpch`-генератором;
  `Engine` создавался заново на каждый прогон, как в CLI.
- Синтетический проект: `directory-per-model`, N простых `entity-model` документов,
  минимальный генератор с одним артефактом (чтобы manifest и cache-hit работали).
- Сценарии: cache-hit (no-op), изменён 1 документ, изменены 2 документа; отдельно —
  parse/composition без кэша и масштабирование N = 8 / 40 / 120.
- Скрипты замеров были временными (в репозиторий не добавлялись); ключевые фрагменты —
  в §9.

## 4. Результаты

### 4.1 TPC-H, полный прогон

| Сценарий | Стена, мс | discovery | fingerprint | parse | generate | write |
|----------|-----------|-----------|-------------|-------|----------|-------|
| incremental, no-op | 67 | 34 | 32 | 0 | 0 | 0 |
| incremental, изменён 1 из 8 | 123 | 34 | 31 | 33 | 8 | 13 |
| incremental, изменены 2 из 8 | 125 | 34 | 31 | 33 | 8 | 13 |

Даже полный cache-hit стоит 67 мс, из которых ~63 мс — повторный разбор YAML
в discovery и fingerprint.

### 4.2 TPC-H, микрозамеры

| Операция | Медиана, мс |
|----------|-------------|
| `load_yaml` всех 8 source-документов | 31.1 |
| sha256 всех 8 документов (10 КБ) | 0.017 |
| discovery как есть | 34.1 |
| discovery без YAML-проверки `format` | 2.3 |
| fingerprint входа | 32.5 |
| `Parser.parse_document` одного документа | 4.6 |
| parse всех 8 документов | 37.3 |
| composition resolve (parse + merge) | 38.4 |

Вывод: 93 % discovery — полный YAML-разбор ради проверки одного ключа; хэширование
тех же файлов дешевле разбора примерно в 1800 раз.

### 4.3 Синтетика: сценарий «изменён один из N»

| N | `load_yaml` всех, мс | sha256 всех, мс | no-op, мс | 1 изменён, мс |
|---|----------------------|-----------------|-----------|----------------|
| 8 | 7.4 | 0.014 | 18 | 40 |
| 40 | 37.1 | 0.023 | 84 | 142 |
| 120 | 124.4 | 0.051 | 294 | 457 |

Стоимость прогона линейна по N и почти не зависит от того, изменился файл или нет:
при N = 120 один изменённый файл стоит столько же, сколько полный прогон без кэша
разбора (457 мс).

### 4.4 Стоимость композиции отдельно

| N | compose-only, без imports, мс | compose-only, с imports, мс |
|---|-------------------------------|------------------------------|
| 8 | 0.8 | 1.7 |
| 40 | 3.3 | 6.0 |
| 120 | 9.9 | 18.2 |

При N = 120 с imports композиция — 4 % прогона (18 из 457 мс). После L2 она станет
заметной долей: 18 из ~35 мс (см. §6), но её нельзя переиспользовать целиком —
изменение любого документа меняет результат слияния.

### 4.5 Проверка сериализации разобранного документа

| Операция | Медиана |
|----------|---------|
| `Parser.parse_document` (TPC-H, `orders`) | 4.6 мс |
| `ModelDocument.model_validate_json` из кэша | 0.044 мс |
| Размер JSON-представления / размер YAML | 1861 Б / 1444 Б (1.29×) |

Разобранный документ сериализуется и восстанавливается структурно идентично
(`model_dump()` совпадает), `entity()`/`enum()`/`type()` работают, поскольку индексы
`_IndexedModel._entity_map` и др. строятся валидатором заново. Обязательное условие:
`path`, `Entity.source`, `Entity.format`/`format_version`, `FieldDef.source` —
path-зависимые поля; в кэше они не хранятся и восстанавливаются при загрузке.
Pydantic-сравнение `==` для этого не годится (сравниваются приватные индексы);
критерий корректности — `model_dump()` + функциональная проверка.

## 5. Почему L3 сам по себе не решает задачу

- L3 (кэш результата композиции) экономит максимум 1 мс на TPC-H и 10–18 мс при
  N = 120 — 2–4 % прогона, пока L2 отсутствует.
- При изменении одного документа ключ композиции меняется, и полный результат
  переиспользовать нельзя; кэшировать можно только разбор документов и разрешение
  imports — это и есть L2, а не L3.
- При cache-hit композиция не выполняется вовсе (L1 уже пропускает прогон).

Поэтому «композиция по fingerprint» в roadmap следует читать как «композиция
переиспользует разбор по fingerprint». Отдельный L3 имеет смысл только как
инкрементальное слияние (кэш промежуточных результатов merge), и это отдельная
более сложная задача.

## 6. Варианты и оценка

### Вариант A — микрооптимизации без нового состояния

1. Проверять `format` в discovery без полного `load_yaml` (чтение головы файла или
   ленивый YAML-парсер), сохранив текущую семантику ошибок: битый YAML по-прежнему
   попадает в `Parser` и даёт `EG000`.
2. Переиспользовать уже разобранный в fingerprint raw-dict при `Parser.parse_document`
   в рамках одного запуска (in-memory, без диска).

| Сценарий TPC-H | Сейчас | после A1 | после A1+A2 |
|----------------|--------|----------|-------------|
| no-op | 67 | ~35 | ~35 |
| изменён 1 из 8 | 123 | ~91 | ~60 |

Выигрыш ~2× на прогон, без нового состояния и без ADR о кэше. Ограничение: no-op
всё равно разбирает все YAML в fingerprint, а CLI-запуск не переиспользует работу
между процессами.

### Вариант B — L2: персистентный content-addressed кэш документов (рекомендуется)

Кэш по ключу SHA-256 от содержимого документа (+ версии Eggpipe, формата и его
`input_paths`-closure) хранит разобранный `ModelDocument` без path-зависимых полей.
Потребители:

- discovery: формат документа берётся из кэша, полный YAML не разбирается;
- fingerprint: imports и разбор — из кэша, на диске читаются и хэшируются только байты;
- parse: изменённые документы разбираются, остальные загружаются из кэша.

Ожидаемая оценка (из §4.2–4.3, компоненты складываются):

| Сценарий | Сейчас | Оценка L2 | Ускорение |
|----------|--------|-----------|-----------|
| TPC-H no-op | 67 | 3–5 | ~15× |
| TPC-H изменён 1 из 8 | 123 | ~30 | ~4× |
| N=120 no-op | 294 | 2–4 | ~100× |
| N=120 изменён 1 из 120 | 457 | ~34 | ~13× |

### Вариант C — L3: кэш результата композиции

Не рекомендуется в 0.5.0: см. §5. После L2 измерить долю композиции в прогоне
(§4.4 даёт 29–53 % при N = 120) и, если она остаётся узким местом, открыть отдельную
задачу на инкрементальное слияние, а не на кэш готового результата.

## 7. Рекомендация

1. Реализовать **вариант B (L2)** в 0.5.0 как продолжение `--incremental`:
   поведение по умолчанию не меняется, новых флагов и полей отчёта нет.
2. Оформить **ADR-0020 «Кэш разбора документов (L2)»**: ключ и инвалидация, место
   состояния, границы доверия, GC, взаимодействие с lock и watch.
3. Обновить System Design: §8.6 (поток incremental) и §9.3 (заменить зарезервированный
   `CacheStrategy` на фактический контракт кэша документов).
4. ТЗ новую версию не требует: контракт CLI/отчёта не меняется; состояние `.eggpipe/`
   описывается в System Design как внутреннее. Если решим публично документировать
   формат кэша, это пойдёт в ТЗ v2.5 вместе с метриками (пункт 3 roadmap).
5. Вариант A полезен как подготовка и fallback, но не заменяет L2: он не убирает
   повторный разбор в fingerprint и не помогает однократному CLI-запуску.
6. Порог приёмки в benchmarks: TPC-H no-op и «изменён 1 из 8» фиксируются в
   `engineering/benchmarks.md` до/после; регрессия no-op запрещена.

## 8. Риски и открытые вопросы для ADR

| Риск / вопрос | Комментарий |
|---------------|-------------|
| Повреждённый или подменённый кэш | Кэш — недоверенный ввод: валидировать через Pydantic, при ошибке — полный разбор, никогда не маскировать `EG000`/`EG028` |
| Path-зависимые поля | `path`, `source`, `format`, `format_version` восстанавливать при загрузке; хранить path-free payload |
| Инвалидация плагинов | Версия формата/генератора уже входит в fingerprint; изменение кода без смены версии — известное ограничение ADR-0017 |
| `input_paths`-closure | Ключ документа должен включать зависимости, объявленные `FormatPlugin.input_paths`, иначе внешний файл не инвалидирует кэш |
| GC и размер | Хранить только записи текущего прогона (prune при записи); JSON ≈ 1.3× исходников: TPC-H ~13 КБ, 1000 документов ~1.3 МБ |
| Запись и конкурентность | Писать под существующим `.eggpipe/lock`, атомарно; кэш не является owned-артефактом и не участвует в `cleanup` |
| Ошибки разбора не кэшировать | Битый YAML/невалидная модель всегда разбираются заново и дают те же коды |
| Watch | CLI создаёт новый `Engine` на прогон (`cli/main.py:494`), поэтому персистентный кэш нужен и для watch; дополнительно кэш должен быть доступен `discovery`, чтобы убрать YAML-проверку |
| Per-entity генерация | `--entity` уже отключает incremental (ADR-0018); L2 наследует это поведение |
| Метрики | Хиты/промахи кэша логично отдать в отчёт вместе с пунктом 3 roadmap (ТЗ v2.5), не в этом PR |

## 10. Non-goals

- Реализация кэша и изменения кода в этом spike.
- Кэш на уровне entity и per-entity watch.
- Метрики и structured logging (пункт 3 roadmap, ТЗ v2.5).
- Автоматическая инвалидация по коду плагина без смены версии.
