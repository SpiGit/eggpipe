# Eggpipe — Техническое задание v2.1

## 1. Цель и назначение

**Назначение:** инструмент (CLI и библиотека), который читает описание модели данных из файла формата YAML и порождает из него артефакты в произвольных целевых форматах (SQL-миграции, JSON-схемы, YAML-конфиги, Python-модели, TypeScript-типы и т.п.).

**Ключевая философия:** один источник истины — YAML-описание модели — и произвольное количество генераторов-«адаптеров», каждый из которых умеет превращать одну и ту же модель в свой формат.

**Ключевые свойства ядра:**

- Ядро **не содержит генераторов** — все генераторы это плагины, подключаемые через entry points.
- Ядро содержит **ровно один встроенный формат** `entity-model` (базовый, формат-нейтральный). Остальные форматы (sql-model, ts-model, и т.п.) регистрируются **плагинами форматов**.
- Сущности в модели **изолированы**: ядро не знает о связях между сущностями (relations). Если связь нужна — она описывается отдельной сущностью или механикой конкретного формата в плагине.
- Все нетривиальные правила (типы, связи, naming, шаблоны) относятся к плагинам; ядро обеспечивает только парсинг, композицию, валидацию базового формата, оркестрацию и запись артефактов.

**Целевая аудитория:** fullstack-команды, разработчики API-first сервисов, инженеры, которым нужна консистентность между схемой БД, спецификацией API и клиентскими типами.

**Способы использования:** CLI (`eggpipe ...`) и библиотека (`Engine`). Библиотечный сценарий — first-class: ядро не должно выполнять глобальных side effect'ов (в частности, не настраивать root-logger и не вызывать `sys.exit`).

### 1.1. Не-цели v1

- Reverse engineering существующей БД, introspection, генерация модели по схеме.
- Выполнение миграций и применение сгенерированного SQL.
- Relations/FK в базовой модели; связи описываются отдельными сущностями или format-плагином.
- Встроенные генераторы и встроенные шаблоны.
- Binary-артефакты (изображения, архивы, скомпилированные файлы).
- Инкрементальная генерация и кэширование в v1.
- GUI/Web-интерфейс.
- Песочница для плагинов: плагины — доверенный код.

## 2. Термины

| Термин | Определение |
|--------|-------------|
| **Документ модели** | YAML-файл с заголовком (`format`, `version`) и секцией `model`. После парсинга — `ModelDocument` (header + imports + модель) |
| **Модель (model unit)** | Одна логическая сущность (`Entity`). В `directory-per-model` собирается из нескольких YAML-слоёв |
| **Исходная модель** | Секция `model` — сущности (`entities`), перечисления (`enums`), пользовательские типы (`types`). После композиции — `SourceModel` |
| **Срез (slice)** | Подмножество скомпонованной модели для конкретного генератора (`ModelSlice`), замкнутое по ссылкам на enums/types |
| **Слой (layer)** | YAML-файл, содержащий данные одного формата для одной модели. Слои одной модели мержатся в порядке наследования форматов |
| **Слой формата** | Часть документа, описанная конкретным форматом; слой-дельта валидируется `layer_entity` этого формата |
| **Итоговый формат** | Самый производный формат среди слоёв модели; по нему валидируется `full_entity` |
| **Resource** | Файл, который не является моделью и не участвует в merge; передаётся генератору через `GenerationContext.imports` |
| **Раскладка источников** | Способ группировки моделей: `monolith`, `file-per-model`, `directory-per-model` |
| **Source** | Файл или каталог из `sources` метаконфига, участвующий в сборке модели |
| **Формат** | Зарегистрированный тип документа. Определяет **парсер**, `layer_entity`, `full_entity`, примитивы и наследование. Базовый формат `entity-model` встроен в ядро; остальные форматы регистрируются плагинами |
| **Формат-плагин** | Плагин, регистрирующий формат (parser + валидация + дополнительные типы/поля) |
| **Генератор** | Плагин, преобразующий срез модели в целевой формат |
| **Шаблон** | Шаблон (формат зависит от генератора), используемый для рендеринга |
| **Артефакт** | Результат генерации: один текстовый файл с относительным path и content |
| **Метаконфиг** | `.eggpipe.yaml` — источники, генераторы, переменные, defaults |
| **Манифест вывода** | Файл `.eggpipe/manifest.json` в каталоге конфига, в котором ядро фиксирует locations и принадлежащие им артефакты |
| **Владение (ownership)** | Артефакт принадлежит location `(generator, output_dir)`, если он записан в глобальном manifest. Только owned-файлы можно перезаписывать и удалять при cleanup |

## 3. Формат исходной модели (YAML)

### 3.1. Структура документа

```yaml
# === Заголовок документа ===
format: entity-model     # имя зарегистрированного формата (обязательно)
version: "1.0"           # опционально: версия СХЕМЫ ФОРМАТА; нет — последняя
metadata: {}             # опционально: расширения format-плагина под его namespace

# === Описание модели ===
model:
  name: string                            # опционально; у импортов не мержится
  description: string                     # опционально
  metadata: {}                            # опционально; ключи namespaced плагином

  imports:                                 # импорты (см. 3.5)
    - path: ./shared/audit-fields.yaml     # YAML-модель: merge, композиция
      as: audit                            # опционально: alias для extends/ссылок
    - path: ./icons/user.svg
      as: avatar_icon                      # произвольный файл: доступен по имени

  entities:
    - name: User
      description: string
      version: "1"                         # опционально: версия сущности
      updated_at: 2026-11-10               # опционально: date или datetime (ISO 8601)
      metadata: {}                         # опционально: расширения формата
      extends: AuditFields                 # опционально (см. 3.5.4)
      fields:
        - name: string                    # имя поля
          type: string                    # примитив или ссылка на enum/type
          description: string
          required: boolean               # default: false
          nullable: boolean               # default: false (см. 3.6)
          default: string | number | boolean | date | datetime | null
                                          # отсутствие ключа = «default не задан»
          constraints:
            min: number | date | datetime
            max: number | date | datetime
            min_length: integer
            max_length: integer
            pattern: string
          metadata: {}                      # опционально: расширения формата

  enums:
    - name: string
      description: string
      metadata: {}
      values:
        - name: string
          value: string | integer          # опционально (default = name)
          description: string

  types:                                  # пользовательские алиасы
    - name: string
      description: string
      metadata: {}
      base: string                        # примитив или другой custom type
      constraints:
        min: number | date | datetime
        max: number | date | datetime
        min_length: integer
        max_length: integer
        pattern: string
```

**Изменения v1.2 относительно v1.1:**

| Было | Стало | Причина |
|------|-------|---------|
| `model` был одновременно документом, композицией и срезом | Явные типы `ModelDocument` → `SourceModel` → `ModelSlice` | Разная ответственность и разные гарантии |
| `imports` только внутри `model` | Parser поднимает `model.imports` в `ModelDocument.imports` | Композиция работает с документом, а не с готовой моделью |
| `model.name` обязателен | Опционален; у импортов не мержится | Импортируемые фрагменты не обязаны иметь имя |
| `metadata` был только у entity/source | `metadata` у entity/field/enum/type/source | Формат-плагины должны добавлять свои данные |
| `constraints` не были описаны у `FieldDef` | Явно добавлены | Соответствие примерам и System Design |
| `default` — только JSON-скаляры | Добавлены `date`/`datetime`; отсутствие ключа отличается от `null` | YAML-даты и explicit null |
| `extends` — путь к файлу | `extends: EntityName` или `{import, entity}` | Однозначное разрешение |
| `required_by_default` | Удалён | Неоднозначная семантика после Pydantic-разбора |

### 3.2. Примитивные типы

| Тип | Описание |
|-----|----------|
| `string` | Строка |
| `text` | Длинный текст |
| `integer` | Целое число |
| `bigint` | Большое целое |
| `boolean` | Логический тип |
| `float` | Число с плавающей точкой |
| `date` | Дата |
| `datetime` | Дата и время |
| `uuid` | UUID |
| `json` | JSON-объект |

Это набор встроенного формата `entity-model`. Пользовательский формат (через плагин формата) объявляет **свой** набор примитивов (`primitive_types`) и может добавлять/переопределять типы (`serial`, `decimal`, `inet` для SQL и т.п.). Набор примитивов закрыт **в рамках конкретного формата**: `FieldDef.type` валидируется против набора выбранного формата плюс `enums`/`types` модели.

**Правила имён (базовый формат):**

| Сущность | Pattern | Примечание |
|----------|---------|------------|
| `entity.name` | `^[A-Za-z_][A-Za-z0-9_]*$` | PascalCase рекомендуется (MG012 — warning) |
| `field.name` | `^[a-zA-Z_][a-zA-Z0-9_]*$` | snake_case не требуется |
| `enum.name`, `type.name` | `^[A-Za-z_][A-Za-z0-9_]*$` | — |
| `enum.values[].name` | `^[A-Za-z_][A-Za-z0-9_]*$` | значение по умолчанию = name |
| `generator.id` | `^[a-z][a-z0-9-]*$` | совпадает с entry point |

Несоответствие pattern — **Error** (MG028). Format-плагин может ослабить/ужесточить правила имён, но не для `generator.id`.

### 3.3. Правила разрешения типов

- Тип, совпадающий с именем `enum` или `type` из модели (после композиции), считается ссылкой на них.
- Ядро **не переписывает** `FieldDef.type`: там остаётся исходная строка. Плагин получает helper'ы `model.resolve_type(field)`, `model.entity()`, `model.enum()`, `model.type()`.
- Неизвестный тип → **Error** валидации (код MG004); MG001 зарезервирован.
- `CustomType.base` может быть примитивом формата или другим `CustomType`. Цепочки разрешаются транзитивно; цикл → **Error** (MG020), глубина цепочки ≤ 10.
- Constraints поля и типа **сливаются по атрибутам**: атрибут, заданный на поле, переопределяет одноимённый атрибут типа; остальные наследуются. Явно заданный на поле `null` сбрасывает constraint.
- Constraints валидируются на применимость к базовому типу: `min_length`/`max_length`/`pattern` — только для строк, `min`/`max` — только для чисел/дат. Неприменимый constraint → **Error** (MG021).
- `min > max` или `min_length > max_length` → **Error** (MG021).

### 3.4. Форматы документа

#### 3.4.1. Заголовок и выбор формата

- Заголовок содержит обязательный `format`; `version` опционален; `metadata` — extension point format-плагина.
- `format` = ключ в **реестре форматов** (FormatRegistry). Неизвестный формат → **Error** (MG007), без «тихого» default `entity-model`.
- `version` — строка; число (`version: 1.0`) нормализуется в `"1.0"`. Если `version` не указан, используется последняя версия формата из `supported_versions`.
- Неизвестная версия → **Error** (MG008).
- **Базовый формат `entity-model` встроен**, формат-нейтральный. Поддерживаемая версия — `"1.0"`.
- Имя `entity-model` зарезервировано ядром; формат-плагин не может его переопределить.
- Формат определяется **только файлами модели**. В `.eggpipe.yaml` нет поля `format`; глобального целевого формата тоже нет.
- Пользовательские форматы регистрируются формат-плагинами через entry points (группа `eggpipe.formats`).

#### 3.4.2. Расширение и наследование форматов

Формат-плагин может расширить другой формат:

```python
class FormatSchema:
    layer_entity: type[BaseModel]
    full_entity: type[BaseModel]


class FormatPlugin(ABC):
    api_version: ClassVar[Literal["1"]]
    format_names: ClassVar[list[str]]
    supported_versions: ClassVar[list[str]]          # упорядоченный; последняя = latest
    extends: ClassVar[str | None] = None
    base_versions: ClassVar[dict[str, str]] = {}     # B version -> A version
    primitive_types: ClassVar[set[str]]
    schemas: ClassVar[dict[str, FormatSchema]]
```

Правила:

- `extends` — имя одного базового формата; множественное наследование не поддерживается.
- Цикл наследования или глубина > 10 → **Error** (MG034).
- `B extends A` означает, что B — надмножество A: B не переименовывает и не удаляет поля A.
- `supported_versions` — упорядоченный список; последняя версия используется, если `version` не указан.
- `schemas` содержит Pydantic-схемы для каждой версии; ключи обязаны совпадать с `supported_versions`.
- `base_versions[B_version] = A_version`: для каждой версии B явно указано, какую версию A она расширяет.
- `primitive_types` наследуются; B может добавлять свои примитивы. Переопределять унаследованный примитив с другим смыслом запрещено (**Error** MG034).
- `layer_entity` — частичная Pydantic-схема одной сущности для файла-слоя. Валидирует только поля этого формата и identity (`name`).
- `full_entity` — итоговая Pydantic-схема сущности после merge слоёв. Для расширения обычно наследует `full_entity` базового формата.
- Для identity в ядре есть `EntityIdentity` (`name`) и `FieldIdentity` (`name`); дельта-модели наследуют их.
- Обязательность новых полей определяет формат: в `layer_entity` поле может быть optional, а в `full_entity` — required.
- Базовый `EntityModelFormat` предоставляет реализации по умолчанию; расширение может переопределить `schemas`, `parse`, `validate`.
- Документ остаётся общим конвертом ядра. First-class поля уровня документа (`postgres.schema`) — future; в v2.1 используются `metadata`.
- Дополнительные поля формата могут быть first-class полями Pydantic-модели. `metadata` остаётся extension point.
- Версии форматов независимы: `entity-model 1.0` и `postgres-model 2.0` — нормально.
- Для версии `V` расширения B базовая версия `base_versions[V]` должна поддерживаться A; иначе MG034.
- `schemas[V].full_entity` должен быть подклассом `A.schemas[base_versions[V]].full_entity`; иначе MG034.

#### 3.4.3. Формат модели и совместимость генераторов

- Каждая модель (сущность) имеет **итоговый формат** — самый производный формат среди её слоёв.
- Итоговый формат и версия доступны генератору через `Entity.format` и `Entity.format_version` (исключены из сериализации).
- Генератор объявляет совместимые форматы:

```python
class GeneratorPlugin(ABC):
    input_formats: ClassVar[set[str] | None]
```

- `input_formats` обязателен: `None` — явно любой формат, `set()` — явно ни один.
- Отсутствие поля — ошибка plugin contract (MG301).

- `None` — генератор принимает любой формат.
- `set()` — генератор не принимает ни один формат.
- `{"entity-model"}` — генератор принимает `entity-model` и всех его наследников.
- `{"postgres-model"}` — генератор принимает только `postgres-model` и его наследников.
- `{"entity-model", "sql-model"}` — принимает оба формата и их наследников.
- Совместимость транзитивна по цепочке `extends`.
- «Принимает A» означает «принимает всех наследников A»; exact-only режима в v2.1 нет.
- В одном запуске допускаются модели разных форматов.
- Проверка выполняется после среза и closure, до `validate_config()`/`generate()`.
- Несовместимость — **pre-flight ошибка всего запуска** (MG033): артефакты не пишутся,
  `--plan`/`--check` также завершаются ошибкой, exit code 2.
- Ошибки собираются по всем генераторам.
- Модель парсится один раз. Отдельного pipeline на генератор нет.
- `GenerationContext.formats` — сводка форматов **среза** (`frozenset[FormatInfo]`).
- Пустой срез: `input_formats` не проверяется, `context.formats` пустой, генератор получает
  пустой `ModelSlice`.
- Глобальные `enums`/`types` с одинаковым именем у сущностей разных форматов → MG002.

#### 3.4.4. Слои формата в одной модели

- В `directory-per-model` одна модель может состоять из нескольких файлов-слоёв.
- Один файл содержит данные **одного** формата. Несколько файлов одного формата в одной модели не поддерживаются (**Error** MG029).
- Все форматы слоёв обязаны образовывать одну цепочку наследования. Несвязанные форматы → **Error** (MG029).
- Порядок слоёв вычисляется по `extends`; состав файлов задаётся явно в `.eggpipe.yaml`.
- Базовый файл — полный: валидируется `full_entity` своего формата.
- Файлы-дельты после базового валидируются `layer_entity` своих форматов.
- После merge итоговая модель валидируется `full_entity` самого производного формата.
- В `monolith` и `file-per-model` файл полный и валидируется `full_entity`; layer merge нет.
- Слой-дельта обязан содержать ровно одну сущность (`model.entities` длиной 1); иначе **Error** (MG031).

**Версии слоёв:**

- Версия каждого файла: явная или последняя версия его формата.
- Для дельты B версии `V_B` базовая версия берётся из `B.base_versions[V_B]`.
- Файл базового формата обязан иметь именно эту версию; иначе MG034.
- Для цепочки C → B → A проверка применяется на каждом шаге.
- Итоговый `Entity.format` / `format_version` — самый производный формат и его версия.
- Если версия не указана и latest не совпадает с требованием зависимости, ошибка просит указать версию явно.
- Неизвестная версия — MG008.


### 3.5. Композиция (Composition)

#### 3.5.1. Раскладки источников

Модель — это одна сущность. Поддерживаются три раскладки:

**Вариант 1: Monolith**

```text
model.yaml           # несколько entities/enums/types в одном файле
```

**Вариант 2: File-per-model**

```text
entities/
  user.yaml          # одна entity
  post.yaml          # одна entity
```

**Вариант 3: Directory-per-model**

```text
entities/
  user/
    base.yaml        # format: entity-model
    postgres.yaml    # format: postgres-model, extends entity-model
    resources/
      avatar.svg
      description.md
```

Правила:

- В `file-per-model` каждый YAML содержит ровно одну сущность.
- В `directory-per-model` каждый файл-слой содержит ровно одну сущность (MG031).
- В `monolith` один файл может содержать несколько сущностей.
- Раскладка и список файлов задаются явно в `.eggpipe.yaml` (§5).
- Формат определяется файлами; в `.eggpipe.yaml` его нет.

**Порядок сборки модели:**

1. Discovery отбирает каталоги моделей и файлы по явным правилам.
2. Для каждого файла разрешается версия: явная или latest.
3. Если у модели один файл — это **полный файл**: он валидируется `full_entity` своего формата.
4. Если файлов несколько — первый (базовый) слой валидируется `full_entity`, остальные
   файлы-дельты — `layer_entity` своих форматов.
5. Слои одной модели упорядочиваются по цепочке `extends`.
6. Проверяется `base_versions`: версия каждого слоя соответствует требованию зависимости.
7. Слои мержатся аддитивно в одну модель.
8. Итоговая модель валидируется `full_entity` самого производного формата.

В `monolith` и `file-per-model` каждый файл — полный: layer merge не выполняется,
пользователь сам пишет данные в конечном формате. В `directory-per-model` с несколькими
файлами базовый файл полный, остальные — дельты.

**Правила discovery:**

- Обход детерминированный, лексикографический по POSIX-пути.
- Пропускаются скрытые файлы/каталоги, `.git`, `.eggpipe`, `__pycache__`, `.venv`, `node_modules`
  и все `output_dir` текущего конфига.
- YAML, не являющийся документом модели, не подхватывается автоматически: он должен быть
  явно указан как resource. Если он всё же попал в `files` (явно или glob) — MG023.
- Повторно найденный resolved-путь обрабатывается один раз (Warning MG024).
- Пустой каталог модели — Warning (MG027) и пропуск.
- Symlink за пределы project root — Error (MG022).

#### 3.5.2. Imports

Два типа:

**A. YAML-модели** (композиция/наследование):
```yaml
format: entity-model
version: "1.0"
model:
  imports:
    - path: ./base-entity.yaml
      as: base
    - path: ../shared/audit-fields.yaml
      as: audit
  entities:
    - name: Post
      extends: AuditFields
      fields:
        - name: title
          type: string
```
YAML-импорты **мержатся** в модель по правилам ADR-0001. Импортированные документы также валидируются как модели и обязаны иметь **тот же `format` и совместимую `version`**, что и импортирующий документ. `as` для YAML-импорта опционален: если не задан, alias = stem файла; alias обязан быть уникальным. Файл с расширением `.yaml`/`.yml` всегда трактуется как YAML-модель; остальные — как ресурс.

**B. Произвольные файлы** (ресурсы для генерации):
```yaml
model:
  imports:
    - path: ./icons/user.svg
      as: avatar_icon
    - path: ./templates/card.html
      as: card_template
```
Произвольные импорты читаются как `bytes` и доступны плагину в `GenerationContext.imports` под именем `as`. Содержимое файлов не парсится ядром; декодирование — задача плагина. `as` обязателен, дубликат `as` → **Error** (MG025).

#### 3.5.3. Правила

- Пути разрешаются относительно файла, где объявлен импорт (`./`, `../` только; абсолютные пути — **Error**).
- Импорт не может выходить за **project root** (каталог `.eggpipe.yaml`); попытка — **Error** (MG022). Для осознанного исключения — флаг `--allow-outside-imports`.
- Импорты транзитивны (из родительских файлов наследуются).
- Циклические импорты — **Error** (MG006) с полным путём: `a.yaml → b.yaml → a.yaml`.
- Глубина импортов ≤ 10 (MG006).
- Совпадения имён (entities/enums/types) между несвязанными файлами — **Error** (MG002).
- Один и тот же resolved-путь обрабатывается один раз независимо от количества импортов.
- Полная семантика composition merge (imports/extends) — **[ADR-0001](../adr/0001-composition-merge-semantics.md)** с уточнениями [ADR-0008](../adr/0008-model-units-and-source-layouts.md).
- `entity.extends` разрешается **только внутри import-closure своего документа**; сущность из другого `source`, не импортированная явно, родителем быть не может (MG009).
- `metadata` мержится аддитивно по namespace; конфликт одинаковых ключей с разными значениями — **Error**.
- Layer merge (несколько форматов одной модели) описан в §3.5.5; его правила строже composition merge.

#### 3.5.4. Entity-level extends

Короткая форма (родитель ищется по уникальному имени среди импортированных документов):

```yaml
# main.yaml
model:
  imports:
    - path: ./shared/audit.yaml
      as: audit
  entities:
    - name: Post
      extends: AuditFields       # имя entity из import-closure
      fields:
        - name: title
          type: string
```

Явная форма (рекомендуется при нескольких кандидатах):

```yaml
entities:
  - name: Post
    extends:
      import: audit              # alias YAML-импорта
      entity: AuditFields
    fields:
      - name: title
        type: string
```

Правила:

- родитель обязан существовать в import-closure; не найден или неоднозначен → **Error** (MG009);
- цепочки `A extends B extends C` разрешены; цикл или глубина > 10 → **Error** (MG009);
- наследуются `description`, `version`, `updated_at`, `metadata` и `fields`; child может переопределить scalar-атрибуты, `metadata` мержится аддитивно, поля с тем же `name` замещают родительские;
- parent-поля — на своих позициях; поле с тем же `name` в child **полностью замещает** родительские атрибуты; новые поля child — в конце;
- дубликат имени поля в итоговой entity → **Error** (MG003).

#### 3.5.5. Layer merge (несколько форматов одной модели)

Правила применяются к слоям `directory-per-model`:

- Merge аддитивный: новые entity/enum/type/field/metadata-ключи.
- Расширение может добавлять поля к существующей сущности.
- Одинаковое имя с разными значениями — **Error** (MG029).
- Переопределение существующих значений не поддерживается.
- Scalar (`description`, `version`, `updated_at`) можно задать только если он ещё не задан; одинаковое значение допустимо.
- `metadata` мержится рекурсивно; конфликт скаляров — **Error** (MG029).
- Поля: сначала поля базового слоя в исходном порядке, затем новые поля в порядке слоёв.
- `EnumDef`: новые enum добавляются; значения существующего enum в v2.1 не расширяются, удаление/переименование запрещено.
- CustomType: новые типы добавляются; изменение базового типа запрещено.
- Базовый слой валидируется `full_entity`; слои-дельты — `layer_entity`; итог — `full_entity`.
- Provenance: `Entity.source` — базовый слой, `Entity.layer_sources` — все слои, `FieldDef.source` — слой, где поле определено.

**Коллекции и merge:**

Для каждой коллекции задаётся `MergePolicy`:

```python
class MergePolicy(str, Enum):
    KEYED = "keyed"      # найти по ключу, дополнить существующий, добавить новый
    APPEND = "append"    # только новые элементы; существующие неизменяемы
    UNION = "union"      # только новые уникальные скаляры
    ERROR = "error"      # коллекцию нельзя менять слоем
```

- `KEYED` — расширяемый список. Порядок базового слоя сохраняется, новые элементы
  добавляются в конец. Существующий элемент рекурсивно мержится; дубликат ключа внутри
  одного слоя — MG029.
- `APPEND` — append-only. Новые ключи добавляются, существующие элементы менять нельзя;
  повторный ключ — MG029.
- `UNION` — для списков скаляров: добавляются только уникальные значения.
- `ERROR` — фиксированный кортеж: нельзя ни добавлять, ни менять (MG029).

Отображение для core-модели:

| Коллекция | Политика | Смысл |
|-----------|----------|-------|
| `model.entities` | `KEYED` | слой обязан содержать одну сущность с тем же именем |
| `entity.fields` | `KEYED` | патч существующих полей + новые поля |
| `model.enums` | `APPEND` | только новые enum; существующие не меняются |
| `enum.values` | `APPEND` | только новые значения; добавление в существующий enum в v2.1 не поддерживается |
| `model.types` | `APPEND` | только новые типы; существующие не меняются |
| `imports` в слоях | `ERROR` | в `directory-per-model` запрещены |
| `metadata`-списки | `APPEND` | аддитивность |

- Политика задаётся на list-поле через `json_schema_extra={"merge": ..., "merge_key": ...}`.
- Core-списки используют значения из таблицы; ключ по умолчанию — `name`.
- Неизвестный список без политики — `ERROR` (MG029).
- `metadata`-словари мержатся рекурсивно; конфликт скаляров — MG029.

### 3.6. Null-семантика

Три независимых измерения поля:

- `required` — значение **обязательно присутствует при создании** после применения `default`. Присутствие означает «явно передано» или «подставлено default». `null` считается переданным значением, но допустим только при `nullable: true`.
- `nullable` — если значение предоставлено, оно может быть `null`. **Default: `false`**.
- `default` — значение, подставляемое, когда поле не указано при создании. Отсутствие ключа `default` в YAML — это **UNSET** («default не задан»), а не `null`.

Ядро проверяет **согласованность описания модели**, а не runtime-поведение приложения. Формат/генератор может накладывать дополнительные правила, но не отменяет ошибки MG010.

**Полная матрица:**

| `required` | `nullable` | `default` | Статус | Смысл |
|:----------:|:----------:|:---------:|--------|-------|
| `true`  | `false` | UNSET | OK | Обязательное непустое поле |
| `true`  | `false` | значение | OK | Обязательное, но может не указываться — подставляется default |
| `true`  | `false` | `null` | **Error MG010** | null невозможен при `nullable=false` |
| `true`  | `true`  | UNSET | OK + Warning MG011 | Обязательное, допускает null; легитимно только для PATCH-семантики, которой в v1 нет |
| `true`  | `true`  | значение | OK + Warning MG011 | Как выше, с default |
| `true`  | `true`  | `null` | OK + Warning MG011 | При отсутствии подставляется null |
| `false` | `false` | UNSET | OK | Поле можно не указывать; допустимость отсутствия в хранилище определяет формат/генератор |
| `false` | `false` | значение | OK | Опциональное, при отсутствии — default |
| `false` | `false` | `null` | **Error MG010** | Явный null противоречит `nullable=false` |
| `false` | `true`  | UNSET | OK | Полностью опциональное (может отсутствовать или быть null) |
| `false` | `true`  | значение | OK | Опциональное, при отсутствии — default |
| `false` | `true`  | `null` | OK | Опциональное, при отсутствии — null |

**Запрещённые комбинации и предупреждения:**

| Комбинация | Серьёзность |
|------------|-------------|
| `nullable=false` и `default=null` (при любом `required`) | **Error** (MG010) |
| `required=true` и `nullable=true` | **Warning** (MG011) |
| `default` не приводится к `type` | **Error** (MG016) |
| `default` нарушает `constraints` или не входит в enum | **Error** (MG017) |

`nullable` — всегда свойство **поля**. Constraints могут быть заданы и на `CustomType`, и на поле; слияние — по правилам §3.3.

### 3.7. Default (без `auto`)

- `default` — **скалярное значение**: `string | number | boolean | date | datetime | null`.
- Отсутствие ключа `default` = UNSET; это **не то же самое**, что `default: null`.
- Никаких `auto`/`generated`/`serial` в базовой схеме.
- Автогенерация (`uuid4` на вставке, `created_at=now()`, `identity`-колонка, `nextval`) — ответственность конкретного **формата/генератора**: например, формат-плагин `sql-model` добавит собственное поле вида `column: {generated: identity}`.
- `default` валидируется против итогового типа (с учётом `CustomType.base`), `constraints` и enum-значений.
- YAML-даты (`2026-11-10`) принимаются как `date`; в артефактах плагин сам приводит их к нужному формату. Для переносимости рекомендуется ISO-строка.

## 4. Принцип «данные отделимы от генерации»

Ключевая идея: **модель — это просто данные**. Нет жёсткой привязки «тип модели» → «генераторы».

Пользователь описывает данные один раз, а в метаконфиге решает:
- Какие сущности взять из модели.
- Какие генераторы применить.
- Какие enum'ы и типы включить.
- Какие `variables` передать генераторам.

Один и тот же набор сущностей может порождать разные артефакты в разных генераторах.

## 5. Метаконфиг `.eggpipe.yaml`

```yaml
version: "1.0"                    # версия схемы метаконфига (обязательна)

defaults:
  naming_convention: snake_case   # подсказка плагинам: ядро НЕ переименовывает модель

variables:                        # переменные, доступные плагинам через context.variables
  env: dev

diagnostics:
  stale_dates: false              # MG014 (opt-in): updated_at vs mtime
  ignore: []                      # коды MG..., которые не нужно показывать

resources:                        # общие ресурсы для всех моделей
  - path: ./shared/templates
  - path: ./shared/fixtures/seed.json
    as: seed

sources:
  - path: ./models                 # file-per-model
    layout: file-per-model
    files: ["*.yaml"]
    input:
      entities: []                # пусто = все
      enums: []
      types: []

  - path: ./models-layered         # directory-per-model
    layout: directory-per-model
    model_dirs: ["*"]                # glob или точный список
    files: ["*.yaml"]              # glob или точный список
    models:                        # опциональный override
      customer:
        files: [base.yaml, postgres.yaml]
        resources: [templates/card.html, assets/**]
    input:
      entities: []
      enums: []
      types: []

generators:
  - id: oracle-ddl
    enabled: true
    input:
      entities: [User, Post]      # срез для этого генератора
      enums: [PostStatus]
      types: []
    output_dir: ./output/oracle   # относительно каталога .eggpipe.yaml
    on_conflict: overwrite        # overwrite | skip | error
    cleanup: off                  # off | prompt | enabled (см. §10)
    options: {}                   # опции плагина; валидируются схемой плагина
```

**Раскладки `sources[].layout`:**

| Layout | Обязательные поля | Смысл |
|--------|-------------------|-------|
| `monolith` | `path` (файл) | Один файл, несколько сущностей |
| `file-per-model` | `path` (каталог), `files` | Один YAML на сущность |
| `directory-per-model` | `path`, `model_dirs`, `files` | Каталог на сущность, несколько слоёв |

- `layout` обязателен для каждого `sources[]`.
- Для `file-per-model` и `directory-per-model` поле `files` обязательно.
- Для `directory-per-model` `model_dirs` и `files` обязательны; скрытых значений по умолчанию нет.
- `monolith` требует файл в `path`; `files`/`model_dirs` запрещены.
- `model_dirs` и `files` — glob (`*`, `**`, `?`, `[...]`) или точный список.
- `models.<dir>` переопределяет `files`/`resources` для конкретного каталога.
- Общие ресурсы задаются в top-level `resources`; ресурсы модели — в `models.<dir>.resources`.
- Ресурсы не парсятся как модель и не мержатся.
- Формат в `.eggpipe.yaml` не задаётся: он определяется файлами.

**Ресурсы:**

- `resources` (top-level) — относительно каталога конфига, доступны всем генераторам.
- `models.<dir>.resources` — относительно каталога модели, только для `directory-per-model`.
- `path` — glob или точный путь; каталог разворачивается в файлы рекурсивно.
- Скрытые файлы/каталоги игнорируются.
- Точный путь не найден → Error; glob без совпадений → Warning.
- Alias по умолчанию: путь без расширения; для модели — `<model_dir>/<path без расширения>`.
- `as` разрешён только для одного файла; для glob/каталога — Error.
- Коллизия alias — MG032.
- Границы: общие ресурсы — внутри каталога конфига; ресурсы модели — внутри каталога модели;
  symlink наружу — MG022. `--allow-outside-imports` применяется и к ресурсам.
- Ресурсы попадают в `GenerationContext.imports` вместе с `imports`; alias обязан быть уникальным.
  Коллизия между ресурсом и импортом — MG032; MG025 — только дубликат `as` внутри импортов документа.
- Ресурсы не фильтруются по `generators[].input`; генератор получает все ресурсы запуска.
- Watch следит за всеми файлами и каталогами ресурсов.

**Пути.** `sources.path`, `model_dirs`, `files`, top-level `resources`, `output_dir` и пути шаблонов разрешаются относительно каталога конфига. `models.<dir>.resources` — относительно каталога модели. Пути из CLI — относительно cwd. `output_dir` обязан быть относительным; `--output/-o` заменяет корень (каталог конфига) для всех генераторов: итоговый путь = `-o / output_dir / artifact.path`.

**Позиционные модели CLI** (`eggpipe generate ./models/blog.yaml`) заменяют `sources` из `.eggpipe.yaml`; `generators[].input` применяется как обычно, `sources[].input` в этом режиме отсутствует. Несколько аргументов объединяются по правилам композиции; несовместимые форматы одной модели — MG029.

**Semantics срезов:** `sources[].input` фильтрует содержимое **своего** source (пусто = всё содержимое этого source) после сборки моделей этого source; после композиции получается модель — union отфильтрованных источников. Имена в `sources[].input` проверяются против содержимого этого source, в `generators[].input` — против итоговой модели. Финальный срез генератора = `generators[].input` (пусто = все), применённый к этой модели. После этого выполняется **closure**: транзитивно добавляются все `enums`/`types`, на которые ссылаются выбранные entities и `CustomType.base`. Срез всегда замыкается по ссылкам; неизвестное имя в любом `input` → **Error** (MG018). У генератора **нет поля `source`** — он работает с составленной срезом моделью целиком.

**Порядок:** discovery → layer validation → layer merge → full validation → composition → глобальная валидация → slice → closure → валидация среза → проверка `input_formats` → `validate_config` плагина → `generate()`.

### 5.1. Подключение

Каждый генератор — **плагин**:
- Уникальный `id` (pattern `^[a-z][a-z0-9-]*$`).
- Реализует контракт `GeneratorPlugin` (§6, детали в System Design).
- Подключается через entry points (группа `eggpipe.generators`).
- Получает данные через `sources` + `input`.
- Проверяет `api_version` при загрузке (§6.2).
- `enabled: false` — плагин не загружается и не валидируется; `-g` его не запускает. Для разового запуска — `--include-disabled`.

### 5.2. Дополнительные правила

- `variables` приводятся к `dict[str, str]`; секреты не логируются и редактируются в `eggpipe config show`.
- `options` валидируются JSON Schema/ Pydantic-моделью плагина; неизвестные ключи — по политике плагина (по умолчанию Warning).
- Несколько генераторов могут писать в один `output_dir`; ядро заранее строит карту владения и обнаруживает конфликты путей до записи (MG042).
- `cleanup: off` — безопасный default; `prompt` работает только в tty, иначе fallback `off` + Warning.
- `on_conflict: overwrite` перезаписывает только owned-файлы; не-owned — лишь с `--force`; `skip` не присваивает чужие файлы (см. §10).

## 6. Контракты плагинов

### 6.1 GeneratorPlugin (генератор)

```python
class DiagnosticLocation(BaseModel):
    file: Path | None = None
    entity: str | None = None
    field: str | None = None
    path: str | None = None            # JSON-path внутри документа

class Diagnostic(BaseModel):
    level: Literal["warning", "error"]
    code: str                          # MG...
    message: str
    location: DiagnosticLocation | None

class GeneratorPlugin(ABC):
    api_version: ClassVar[Literal["1"]]   # версия контракта; ядро проверяет
    id: ClassVar[str]                     # должен совпадать с entry point id
    name: ClassVar[str] = ""              # человекочитаемое имя; default → id
    input_formats: ClassVar[set[str] | None]
                                          # None = любой формат; set = форматы и наследники

    @abstractmethod
    def generate(self, input: GeneratorInput) -> GenerationResult: ...

    def validate_config(self, config: GeneratorConfig) -> list[Diagnostic]:
        return []
```

**Вход** (`GeneratorInput`): *целиком* составленный и отфильтрованный (по срезу) `ModelSlice`, `GenerationContext` (variables, naming hint, imports, source paths, `formats`, `run_id`, `config_dir`) и `GeneratorConfig` из `.eggpipe.yaml`. **AppConfig (технические настройки) плагину не передаётся.**

- `ModelSlice` содержит сущности разных форматов; формат каждой сущности — `Entity.format` / `Entity.format_version`.
- `GenerationContext.formats` — сводка форматов **среза** (`frozenset[FormatInfo]`).
- `GenerationContext.format` / `format_version` отсутствуют: формат сущности — `Entity.format`.
- Ядро проверяет все сущности среза против `input_formats` до `generate()` (MG033). Несовместимость — pre-flight ошибка всего запуска, exit 2, артефакты не пишутся.
- Пустой срез: проверка не выполняется, `context.formats` пустой, генератор получает пустой `ModelSlice`.

**Выход** (`GenerationResult`): список `Artifact`; каждый артефакт содержит **относительный POSIX-путь** (`path`) и `content` (text, UTF-8, LF, без BOM). Финальный путь = `output_dir` + `artifact.path`. Имена файлов — зона плагина; ядро выполняет проверку нормализации и границ.

**Правила контракта:**

- Если `GenerationResult.errors` непустой, артефакты этого генератора **отбрасываются** и не пишутся.
- `warnings`/`errors` — структурированные `Diagnostic`, а не строки.
- Исключение из `generate()`/`validate_config()` ловится ядром, преобразуется в ошибку генератора; остальные генераторы продолжаются (exit 1).
- Плагин **не пишет файлы сам** и не меняет `GeneratorInput`/`GenerationContext`; входные модели immutable.
- Text-only: binary-артефакты — не-цель v1.

#### 6.1.1. Decorator API

Основной способ объявления генератора — декоратор `@generator`.

```python
from eggpipe import (
    Artifact,
    GeneratorConfig,
    GenerationContext,
    ModelSlice,
    generator,
)


@generator(
    id="tpch",
    name="TPC-H",
    input_formats={"entity-model"},
)
def tpch(
    model: ModelSlice,
    context: GenerationContext,
    config: GeneratorConfig,
) -> list[Artifact]:
    ...
```

Правила:

- `@generator` — тонкая обёртка над `GeneratorPlugin`; создаёт класс-адаптер.
- `id` опционален: по умолчанию имя функции с `_` → `-`.
- `name` опционален: по умолчанию human-readable имя из функции.
- `input_formats` обязателен; `None` — явно любой формат.
- `api_version` опционален, default `"1"`.
- Аргументы функции инжектятся по аннотациям:
  - `ModelSlice`;
  - `GenerationContext`;
  - `GeneratorConfig`.
- Неизвестная аннотация — ошибка plugin contract (MG301).
- Возвращаемое значение:
  - `GenerationResult`;
  - `Artifact`;
  - `list[Artifact]` / `tuple[Artifact, ...]`.
- Другие return types — ошибка plugin contract.
- Entry point указывает на декорированную функцию:
  ```toml
  [project.entry-points."eggpipe.generators"]
  tpch = "tpch_generator.generator:tpch"
  ```
- Декоратор регистрирует класс-адаптер; `eggpipe gen list/info` работают без изменений.
- Классовый `GeneratorPlugin` остаётся advanced-API для сложных случаев.
- Сигнатура проверяется при загрузке плагина, а не при импорте модуля.

### 6.2 Versioning plugin API

- `api_version` плагина проверяется ядром при загрузке.
- Несовместимый плагин **не ломает** запуск, если он не выбран: он показывается в `eggpipe gen list` как incompatible с Warning.
- Если несовместимый генератор выбран явно (`-g`) или указан в `.eggpipe.yaml` как enabled → **exit 2** с понятной ошибкой (distribution, версия плагина, требуемая версия ядра).
- Публичный API ядра (`eggpipe.__init__`) экспортирует стабильно: `GeneratorPlugin, GeneratorInput, GenerationResult, Artifact, GenerationContext, FormatInfo, FormatSchema, ImportedFile, SourceModel, ModelSlice, Entity, EntityIdentity, FieldIdentity, FieldDef, EnumDef, CustomType, GeneratorConfig, NamingStyle, transform, Diagnostic, EngineReport, Engine, AppConfig, GeneratorRules, GeneratorRulesLoader, FormatRegistry, FormatPlugin, EntityModelFormat, MergePolicy, generator, Provenance, git_provenance, UNSET, PRIMITIVE_TYPES, Constraints` и базовые исключения. Всё остальное (`core.*`, внутренние `engine.*`) — внутренняя реализация и может меняться.
- `Engine` предоставляет `build()`, `generate()` и `check()`; `check()` не пишет файлы и при drift возвращает `success=false`, exit 1.
- Пакет поставляет `py.typed`; публичные имена входят в `__all__`.
- Политика deprecation: применяется после первого публичного релиза; до релиза контракт может меняться без deprecated-полей. `api_version = "1"` — первый стабильный контракт.
- `GenerationContext.format` / `format_version` отсутствуют; использовать `GenerationContext.formats` и `Entity.format`.

### 6.3 FormatPlugin (формат)

Плагин формата регистрирует новый формат (пример `sql-model`) в реестре:

```python
class FormatPlugin(ABC):
    api_version: ClassVar[Literal["1"]]
    format_names: ClassVar[list[str]]          # ["sql-model", ...]
    supported_versions: ClassVar[list[str]]    # упорядоченный; последняя = latest
    extends: ClassVar[str | None] = None       # базовый формат
    base_versions: ClassVar[dict[str, str]] = {}  # B version -> A version
    primitive_types: ClassVar[set[str]]        # примитивы формата
    schemas: ClassVar[dict[str, FormatSchema]]

    @abstractmethod
    def parse(self, raw: dict, base_path: Path) -> ModelDocument: ...

    def validate(self, document: ModelDocument) -> list[Diagnostic]:
        return []
```

- Имя формата совпадает с `format` в заголовке; `entity-model` зарезервирован.
- `version` опционален: нет версии — последняя из `supported_versions`.
- Несовпадение `version` с `supported_versions` → MG008.
- `extends` — одиночное наследование; цикл или глубина > 10 → MG034.
- `B extends A` — B надмножество A; переименование/удаление полей A запрещено.
- `base_versions` задаёт зависимость версий: `B_version -> A_version`.
- `primitive_types` наследуются; добавление разрешено, переопределение смысла — MG034.
- `schemas` содержит `FormatSchema` для каждой версии.
- `layer_entity` валидирует слой-дельту; `full_entity` — итоговую сущность после merge.
- `EntityModelFormat` — базовый класс с готовым parser/validator; расширение переопределяет hooks и при необходимости Pydantic-модели.
- Дополнительные поля могут быть first-class полями Pydantic-модели; `metadata` остаётся extension point.
- `format`/`version` передаются генератору через `Entity.format` / `Entity.format_version`; сводка — `GenerationContext.formats`.
- Формат определяется файлами; `.eggpipe.yaml` его не задаёт (§3.4).

## 7. Шаблонизация

Механизм шаблонов — зона генератора. Ядро передаёт:
- Срез модели (`ModelSlice`).
- `GenerationContext` (`variables`, imports, naming hint, `formats`, per-entity `Entity.format`).
- `GeneratorConfig` (в том числе пути templates от пользователя).

Каждый генератор может:
- Использовать свой движок (Jinja2, Mako, etc); ядро не предоставляет шаблонизатор.
- Поставлять шаблоны внутри wheel через `importlib.resources`.
- Позволять пользователю переопределять шаблоны (паттерн согласуется плагином через `options`, например `options.templates_dir`).
- Валидировать путь шаблонов и выдавать понятную ошибку, если шаблон не найден.

## 8. CLI

### 8.1. Команды (единый подкомандный стиль)

```bash
# Генерация

# Watch (dev-режим)
eggpipe watch                                                     # все

# Конфигурация
eggpipe init [PATH] --layout file-per-model|directory-per-model|monolith
eggpipe config show                                               # merged config + resolved paths
eggpipe config validate                                           # схема + источники + plugin options
eggpipe config schema                                             # JSON Schema .eggpipe.yaml

# Модели
eggpipe model validate ./models/blog.yaml
eggpipe model schema --format postgres-model [--version 2.0]

# Плагины
```

### 8.3. Переменные (`--var`)

- Источники: `--var KEY=VALUE` (CLI) и `variables:` в `.eggpipe.yaml`.
- Приоритет: **CLI > `.eggpipe.yaml`**; при повторном `--var` побеждает последний.
- Ключ обязан быть непустым; `--var` без `=` или с пустым ключом → usage error (exit 2).
- Все значения приводятся к строкам; `= ` в значении допустим (`split("=", 1)`).
- Ядро собирает `context.variables: Mapping[str, str]` (read-only) и передаёт всем плагинам.
- Ядро **никогда не применяет variables молча** — как именно их использовать в форматах/именах/шаблонах, решает плагин.
- Значения не логируются; `eggpipe config show` редактирует переменные, похожие на секреты (`*token*`, `*secret*`, `*password*`), если не задан `--show-secrets`.

### 8.4. Выходные коды и поведение при ошибках

- Если один генератор упал — **остальные продолжаются** (кроме pre-flight несовместимости форматов).
- Несовместимость `input_formats` — config error, exit 2, весь запуск останавливается до генерации.
- Exit code `0` — успех; `1` — были errors при парсинге/валидации/генерации (в т.ч. `--strict` warnings) или drift при `--check`; `2` — config/usage error (некорректные флаги, недоступный `.eggpipe.yaml`, неизвестный generator id, `api_version` mismatch, ошибка загрузки выбранного плагина, MG033/MG034/MG301/MG302); `130` — прерывание Ctrl+C.
- Ошибка парсинга модели — `1`; ошибка схемы `.eggpipe.yaml` — `2`.
- `--dry-run`/`--plan` не создают каталоги и не меняют файлы; exit code отражает план (конфликты — 1).

### 8.5. Watch

- `eggpipe watch` принимает те же флаги генерации (`-g`, `--var`, `--strict`, `--output-format`).
- При старте выполняется первичная генерация.
- Игнорируются: все `output_dir`, `.git`, `.eggpipe`, `__pycache__`, `.venv`, `node_modules`, temp-файлы.
- Изменение `.eggpipe.yaml` перезагружает конфиг; плагины не перезагружаются (для этого нужен перезапуск).
- Debounce (`watch_debounce_ms`, default 300) и batch изменений; CLI: `--debounce-ms`.
- Ошибки генерации не останавливают watch; Ctrl+C — корректное завершение, exit 0.

### 8.6. Init

- `eggpipe init [PATH] --layout file-per-model|directory-per-model|monolith` создаёт `.eggpipe.yaml`
  и пример модели.
- `--layout` обязателен в non-tty; в tty можно спросить.
- Существующий файл не перезаписывается без `--force`.
- `eggpipe init` не устанавливает плагины.

### 8.7. Машиночитаемый вывод

- `--output-format json` печатает в stdout только JSON-отчёт (см. System Design §7.4), логи — в stderr/file.
- Схема отчёта версионируется: `report_version: 2`.
- `--quiet` не подавляет JSON-отчёт; подавляет только человекочитаемые сообщения.
- Цвет/emoji не попадают в JSON.

Структура:

```json
{
  "report_version": 2,
  "run_id": "...",
  "success": true,
  "exit_code": 0,
  "diagnostics": [],
  "formats": [
    {"name": "entity-model", "version": "1.0", "entities": 2}
  ],
  "generators": [
    {
      "id": "tpch",
      "name": "TPC-H",
      "status": "ok",
      "input_formats": ["entity-model"],
      "formats": [{"name": "entity-model", "version": "1.0"}],
      "duration_ms": 7
    }
  ],
  "artifacts": [
    {
      "generator": "tpch",
      "path": "postgres/schema.sql",
      "action": "create",
      "sha256": "..."
    }
  ],
  "manifest": {
    "manifest_version": 2,
    "locations": [
      {"generator": "tpch", "output_dir": "generated", "artifacts": 2}
    ]
  },
  "stale_locations": [],
  "timings": {
    "discovery_ms": 1,
    "parse_ms": 2,
    "validate_ms": 1,
    "generate_ms": 7,
    "write_ms": 3,
    "total_ms": 14
  }
}
```

- `artifacts` — плоский список с `generator`; в `generators[]` артефакты не дублируются.
  `action` принимает `create | update | skip | delete | conflict | error | drift`.
- `generators[].status` принимает `ok | error | skipped`.
- `formats` — глобальная сводка по срезу.
- `manifest` — только locations, без полного списка артефактов.
- `stale_locations` — для MG051.
- Пути — относительные POSIX от каталога конфига.

### 9.2. Валидация результатов генерации

Каждый генератор отвечает за валидацию своего вывода. Ядро выполняет **свои** проверки:

- `artifact.path` — относительный POSIX-путь, без `..`, `.`, абсолютных путей, NUL, backslash, drive-letter, зарезервированных имён; не выходит за границы `output_dir` (MG040).
- Дубликаты путей внутри `GenerationResult` и между генераторами/локациями: exact, casefold,
  prefix (`foo` vs `foo/bar`) — MG042.
- `content` — строка, UTF-8, LF, без BOM (MG040).
- Конфликт ownership / `on_conflict: error` (MG041).
- `on_conflict: skip` для не-owned файла: файл не трогается и не попадает в манифест (Warning MG043).
- Ошибки одного генератора **не отменяют** других (см. §8.4).

### 9.3. Каталог кодов

Коды стабильны и документируются. Диапазоны:

| Диапазон | Область | Фактические коды |
|----------|---------|------------------|
| MG0xx | Документ, YAML, формат/версия, discovery/layers | MG000, MG007, MG008, MG027, MG029, MG031, MG032, MG034–MG038 |
| MG1xx | Модель: типы, имена, default, null-matrix | MG001, MG003–MG005, MG010–MG017, MG019–MG021, MG026, MG028 |
| MG2xx | Композиция, импорты, extends, срезы | MG002, MG006, MG009, MG018, MG022–MG025 |
| MG301 | Конфигурация, plugin API, engine | MG030, MG033, MG300–MG302 |
| MG4xx | Запись артефактов, ownership, planning | MG040–MG043 |
| MG5xx | Cleanup/manifest | MG050–MG052 |

Диапазоны семантические: MG030/MG033 относятся к config/engine, MG300–MG302 — к plugin API.
Полный список с сообщениями ведётся в `docs/user/reference/diagnostics.md`.

### 9.4. `--strict` и игнорирование

- `--strict` повышает warnings до errors (уровень повышается, exit code 1).
- `MG014` выполняется только при `diagnostics.stale_dates: true` (opt-in; file-per-model).
- `--ignore MG014,MG012` и `diagnostics.ignore` игнорируют **только warnings**.
- Errors игнорировать нельзя: код error в `ignore` всё равно показывается.
- Фильтрация выполняется до `--strict`: игнорируемый warning не становится error.
- Plugin warnings участвуют в `--strict`; plugin errors — всегда errors.
- Ошибки валидации модели не позволяют запустить ни один генератор; ошибки одного генератора не мешают остальным.

## 10. Запись артефактов

### 10.1. Пути

- **Финальный путь** = `output_dir` + `Artifact.path`. `output_dir` берётся из `generators[].output_dir` (относительно каталога `.eggpipe.yaml`); `-o` заменяет корень.
- `Artifact.path` — относительный POSIX-путь. Запрещены: абсолютные пути, `..`, `.`, пустые сегменты, `\`, NUL, drive-letter, имена `CON/PRN/AUX/NUL/COM1..9/LPT1..9`, завершающие точка/пробел, сегменты длиннее 255 и путь длиннее 4096.
- Зарезервированы `.eggpipe/`, `.eggpipe-*`, `.eggpipe/manifest.json`; плагин не может их создавать.
- Путь нормализуется в NFC; case-insensitive коллизии (`User.sql` vs `user.sql`) — **Error** MG042.
- Symlink'и: после `resolve()` путь обязан оставаться внутри `output_dir`; symlink-родитель, ведущий наружу, — **Error** MG040. Проверка выполняется и перед записью (TOCTOU остаётся, но окно минимизируется).

### 10.2. Ownership и on_conflict

- Ownership хранится в **глобальном manifest** `.eggpipe/manifest.json` в каталоге конфига.
- Владелец артефакта определяется парой `(generator, output_dir)` + `path`.
- `output_dir` в manifest — путь относительно каталога конфига; `-o` меняет базу, поэтому
  расположения могут быть разными.
- `on_conflict`:
  - `overwrite` (default) — перезаписать **owned**-файл текущего location. Для не-owned файла — **Error** MG041.
  - `skip` — не трогать существующий owned-файл; записать `skipped: true` с текущим `sha256`.
    Для не-owned файла — не трогать, не добавлять в manifest, Warning MG043.
  - `error` — прервать генератор с ошибкой (артефакт + путь).
- `--force` разрешает перезапись **только unowned** файла (нет ни в одном location).
- `--force` **не отбирает** файл у другого generator/location: это MG041, нужно сначала `eggpipe clean`
  или удалить старый manifest.
- Два генератора/локации не могут претендовать на один путь: exact, casefold и prefix-конфликты
  (`foo` vs `foo/bar`) — **Error** MG042 до записи.
- `--force` не обходит MG042.

### 10.3. Глобальный manifest

Один файл на проект: `.eggpipe/manifest.json` в каталоге `.eggpipe.yaml`.

```json
{
  "manifest_version": 2,
  "locations": [
    {
      "generator": "oracle-ddl",
      "output_dir": "output/oracle",
      "eggpipe_version": "0.1.0",
      "plugin_version": "1.2.0",
      "formats": [
        {"name": "entity-model", "version": "1.0"}
      ],
      "generated_at": "2026-11-11T12:34:56Z",
      "artifacts": [
        {"path": "user.sql", "sha256": "...", "skipped": false}
      ]
    }
  ]
}
```

- `manifest_version: 2`; manifest v1 не поддерживается — старые `.eggpipe` нужно удалить.
- Ключ location — `(generator, output_dir)`.
- `formats` — форматы среза генератора, сортировка детерминированная.
- Per-artifact формат не хранится: артефакт может агрегировать несколько сущностей/форматов.
- Manifest пишется атомарно после каждого успешно записанного генератора.
- В manifest попадают только артефакты соответствующего location.
- `skipped: true` означает, что ядро не писало файл; cleanup его не удаляет.
- `.eggpipe/` рекомендуется добавить в `.gitignore`; manifest не предназначен для коммита.
- При `--check` и `--plan` manifest не обновляется.

### 10.4. Atomicity и блокировки

- Запись — в staging-каталог внутри того же `output_dir` (та же ФС), затем `os.replace`.
- Сначала все проверки конфликтов, потом запись. Ошибка до записи не оставляет файлов.
- Глобальный lock `.eggpipe/lock` (O_EXCL, PID) на весь запуск `generate`/`clean`.
- `--plan`/`--check` не берут lock и не меняют файлы.
- Batch-транзакции на несколько файлов нет: при аварийном завершении возможен частично
  обновлённый набор. Manifest обновляется после каждого генератора; следующий запуск
  обнаруживает расхождение по хешам.
- Staging-каталоги `.eggpipe-staging-<pid>-<uuid>` удаляются при старте и по сигналу.

### 10.5. Cleanup

- Cleanup работает только с owned-артефактами из глобального manifest.
- `skipped: true` никогда не удаляется.
- Cleanup в рамках `generate` выполняется только для текущего location успешно завершившегося
  генератора; артефакты, которых нет в новом результате, — кандидаты на удаление.
- Кандидат удаляется, только если текущий `sha256` совпадает с manifest. Если файл изменён
  вручную — Warning MG050 и файл сохраняется.
- `cleanup`:
  - `off` — default, ничего не удалять;
  - `prompt` — fallback `off` + Warning MG030;
  - `enabled` — удалять неизменённые stale-артефакты.
- `eggpipe clean` работает **только по manifest**, без `.eggpipe.yaml` и без установленных плагинов:
  - обходит все locations, включая удалённые генераторы и старые `output_dir`;
  - удаляет unchanged owned-артефакты;
  - изменённые вручную — MG050, остаются;
  - удаляет пустые locations;
  - если locations не осталось, удаляет manifest;
  - `--dry-run` показывает план; для non-tty нужен `--yes`.
- Если у генератора изменился `output_dir`, старый location остаётся в manifest до `eggpipe clean`.
  При генерации выдаётся Warning MG051 «stale generated location».
- Если генератор удалён из `.eggpipe.yaml`, его location остаётся до `eggpipe clean`.

### 10.6. Проверка актуальности

- `eggpipe generate --check` сравнивает ожидаемые артефакты с файлами; при drift — exit 1, файлы не пишутся.
- `--check` предупреждает (MG051), если в manifest есть stale locations.
- `--plan` показывает действия: `create`, `update`, `skip`, `delete`, `conflict`.
- Отчёт `--output-format json` содержит план и итог.

## 12. Требования к качеству

### 12.1. Тесты

- ≥ 80% покрытия ядра.
- Property-based (hypothesis): parser на произвольном dict не падает «сырыми» `KeyError`/`TypeError`/`AttributeError` — только доменные ошибки; round-trip `SourceModel → dict → SourceModel` консистентен с учётом `UNSET`, `date`/`datetime` и заполнения enum values; strategy строит валидные и невалидные модели (в валидных — все проверки проходят, в невалидных — ровно ожидаемая ошибка с кодом).
- Integration: полный цикл CLI → config → parse → composition → slice → generate → write → cleanup.
- **Golden-file тесты**: фикстуры моделей → ожидаемые артефакты. Так как встроенных генераторов нет, golden-тесты используют **reference-плагин** из `examples/`.
- Merge-семантика (ADR-0001) — тест на каждое правило (1–16).
- **Contract-тесты** plugin API: reference-генератор и reference-format проходят публичный контракт; тесты совместимости `api_version`.
- **Security-тесты**: path traversal, symlink, cleanup, импорт вне project root, duplicate keys, YAML aliases, секреты в логах.
- **Determinism-тесты**: повторный запуск даёт идентичные байты артефактов; порядок source/artifact/plugin стабилен; нет абсолютных путей.
- **Cleanup-тесты**: modified-файл не удаляется; чужой файл не удаляется; shared `output_dir`.
- **Concurrency-тесты**: второй запуск при held lock.

### 12.2. Производительность

- Benchmark-методика: фиксированная модель на 1000 entities / 100 enums / 100 types; 5 прогонов после прогрева; медиана; reference-машина указывается в CI.
- Цели: parse+compose+validate ≤ 500 мс; slice ≤ 100 мс; overhead ядра на генератор ≤ 50 мс. Цифры уточняются после первого прототипа; критерий — отсутствие деградации > 20% между релизами.
- Отдельно измеряется lazy-import: `eggpipe --help` не должен импортировать `watchdog`.

### 12.3. Документация

## 14. Открытые вопросы

| Вопрос | Статус |
|--------|--------|
| Инкрементальная генерация | Future; manifest-хеши — основа |
| Кэширование в watch | Простой watch в MVP, интерфейс `CacheStrategy` заложен |
| Machine-readable вывод CI | `--output-format json`; базовая схема в v0.1, расширенная — v0.3 |
| YAML-диалект | Решено: YAML 1.2 через `ruamel.yaml`, duplicate keys → Error |
| Mixed formats в одном запуске | Решено: разрешены; несовместимый генератор — MG033 |
| Несколько файлов одного формата в модели | Не поддерживается в v2.1; future |
| Override значений при layer merge | Не поддерживается в v2.1; future |
| Авто-discovery ресурсов | Только явно в v2.1; future |
| `imports`/`extends` в файлах-слоях | Не поддерживаются в v2.1; future |
| Binary-артефакты | Не-цель v1; отдельный `BinaryArtifact` — future |
| Library API stability | `Engine`/`EngineReport` стабильны с v0.1; политика deprecation — §6.2 |
| Patch-семантика (partial update поверх required) | Future; в v1 `required+nullable` — Warning MG011 |
| `--plugin` (dev, без установки) | Реализован как dev-only флаг |
| Provenance (git-дата сущности для вставки в артефакт без diff-шума) | v0.3; `Entity` должен получить source-ссылку до публичного API |
| Per-entity `generate()` (упрощённые плагины) | Future; новый метод не ломает контракт v1 |
| GUI/Web | Не нужен |
| Публикация PyPI-имени `eggpipe`, CLI `eggpipe` | Проверить доступность; при конфликте — `mdgen`/`metagen` |

## 15. Пример end-to-end

### 15.1. Модель: `model.yaml`

```yaml
format: entity-model
version: "1.0"

model:
  name: blog-platform
  imports:
    - path: ./shared/audit.yaml
      as: audit
  entities:
    - name: User
      version: "1"
      updated_at: 2026-11-10
      fields:
        - {name: id, type: uuid, required: true}
        - {name: email, type: string, required: true}
        - name: username
          type: string
          required: true
          constraints:
            min_length: 3
            max_length: 50
        - {name: bio, type: text, nullable: true}          # optional + nullable

    - name: Post
      extends: AuditEntity
      fields:
        - {name: id, type: uuid, required: true}
        - name: title
          type: string
          required: true
          constraints: {min_length: 1, max_length: 255}
        - {name: content, type: text, nullable: true}
        - {name: status, type: PostStatus, required: true, default: draft}
        # SQL-специфика (identity, generated created_at) — metadata плагина sql-model

  enums:
    - name: PostStatus
      values:
        - name: draft
        - name: published
        - name: archived

  types:
    - name: MediumText
      base: text
      constraints: {max_length: 5000}
```

```yaml
# shared/audit.yaml
format: entity-model
version: "1.0"
model:
  entities:
    - name: AuditEntity
      fields:
        - {name: created_at, type: datetime, required: true}
```

### 15.2. Метаконфиг: `.eggpipe.yaml`

```yaml
version: "1.0"

defaults:
  naming_convention: snake_case

variables:
  env: dev

sources:
  - path: ./model.yaml
    layout: monolith
    input:
      entities: []
      enums: []
      types: []

generators:
  - id: oracle-ddl
    enabled: true
    input:
      entities: [User, Post]
      enums: [PostStatus]
    output_dir: ./output/oracle
    on_conflict: overwrite
    cleanup: off
    options:
      tablespace: USERS

  - id: ts-types
    enabled: true
    input:
      entities: [User, Post]
    output_dir: ./output/ts
```

### 15.5. Directory-per-model со слоями форматов

```text
models/
  customer/
    base.yaml          # entity-model
    postgres.yaml      # postgres-model extends entity-model
    resources/
      customer.md
  orders/
    base.yaml
```

```yaml
# models/customer/base.yaml
format: entity-model
version: "1.0"
model:
  entities:
    - name: Customer
      description: Customer master data
      fields:
        - {name: id, type: integer, required: true}
        - {name: name, type: string, required: true}
```

```yaml
# models/customer/postgres.yaml
format: postgres-model
version: "2.0"          # postgres-model 2.0 расширяет entity-model 1.0
model:
  entities:
    - name: Customer
      metadata:
        postgres:
          table: customer
          primary_key: [id]
      fields:
        - name: id
          metadata:
            postgres:
              type: integer
```

```yaml
# .eggpipe.yaml
sources:
  - path: ./models
    layout: directory-per-model
    model_dirs: ["*"]
    files: ["*.yaml"]
    models:
      customer:
        resources: ["resources/**"]

generators:
  - id: sql
    output_dir: ./generated/sql      # input_formats = {"entity-model"} в плагине
  - id: pg-only
    output_dir: ./generated/pg       # input_formats = {"postgres-model"} в плагине
```

`input_formats` объявляется в классе генератора, а не в `.eggpipe.yaml`.

Итог для `Customer` — `postgres-model 2.0`; для `Orders` — `entity-model 1.0`. `sql` примет обе модели,
`pg-only` завершится ошибкой MG033 на `Orders`.
