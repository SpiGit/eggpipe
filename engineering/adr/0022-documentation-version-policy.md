# ADR-0022: Политика версий в документации

- **Статус:** принято
- **Дата:** 2026-11-25
- **Связанные документы:** [Release guide §«Версия в документации»](../release.md), [ADR-0015](./0015-branching-and-release-policy.md), [ADR-0014](./0014-beta-status-and-compatibility.md), [ТЗ v2.5](../requirements/v2.5.md), `tools/check_docs.py` (DOC161), `tools/bump_version.py`, `.github/workflows/pages.yml`

---

## 1. Контекст

Версия пакета хранится в `pyproject.toml` (`[project].version`), а `src/eggpipe/version.py`
держит её зеркало для рантайма. До PR #51 живые документы (README, `docs/**`, System Design,
`docs/ai/**`) дублировали текущую версию вручную: при каждом релизе её приходилось править
в нескольких местах, и расхождения обнаруживались уже после публикации.

PR #51 ввёл три механизма:

- проверку `DOC161` в `tools/check_docs.py` — литерал текущей версии вне allowlist и вне
  код-фенсов считается ошибкой CI;
- allowlist документов, где конкретные версии — данные, а не утверждение о текущем
  состоянии (`CHANGELOG.md`, `engineering/session-log.md`, `engineering/reviews/`,
  `engineering/adr/`, `engineering/requirements/`, `engineering/roadmap.md`,
  `engineering/backlog.md`, `.github/pull_request_template.md`, `examples/`);
- `tools/bump_version.py` — единственный вход релиза: обновляет `pyproject.toml` и
  `version.py`, переносит `[Unreleased]` в CHANGELOG, выполняет `uv lock` и пересобирает
  `docs/ai`. Версия документации для `mike` вычисляется из `pyproject.toml` в
  `.github/workflows/pages.yml`, отдельного источника нет.

Правило описано только в [release guide](../release.md) — то есть воспринимается как шаг
релиза. На практике оно действует шире: любая правка живого документа может внести литерал
текущей версии, и CI проверяет это на каждом PR. Потребители правила — авторы PR, CI,
релизный скрипт и workflow публикации документации; им нужна нормативная база, а не раздел
релизного чек-листа. Поэтому решение фиксируется ADR.

## 2. Решение

1. **Один источник версии.** Текущая версия объявляется только в `pyproject.toml`;
   `src/eggpipe/version.py` — зеркало, которое обновляет `tools/bump_version.py`. Никакой
   другой файл не объявляет текущую версию.
2. **Живые документы не хардкодят версию.** Под живыми понимаются документы, описывающие
   текущее состояние: README, `docs/**`, System Design, `AGENTS.md`, `CONTRIBUTING.md`,
   `opencode.json` и workflows. Допустимые формы: плейсхолдер `X.Y.Z`, ссылка на
   `pyproject.toml`/`CHANGELOG.md`, генерируемые значения (`docs/ai/manifest.json`, версия
   из пакета).
3. **Исторические записи содержат версии как данные.** CHANGELOG, session-log, ревью, ADR,
   требования (включая актуальное ТЗ), roadmap (метки вех), backlog, PR-шаблон и примеры
   не переписываются задним числом; их список и есть allowlist `DOC161`
   (`PACKAGE_VERSION_ALLOWLIST` в `tools/check_docs.py`). Allowlist не расширяется ради
   удобства: изменение списка — изменение политики.
4. **`DOC161` — эвристический гейт.** Проверка ищет литерал текущей версии вне allowlist и
   вне код-фенсов. Ложное срабатывание на чужой пакет, запиненный на ту же строку в прозе,
   лечится переформулировкой текста (перенос пина в код-фенс или запись без литерала), а не
   правкой allowlist.
5. **Релиз — одной командой.** `tools/bump_version.py` остаётся единственным входом
   подготовки релиза; `mike`-версия документации по-прежнему вычисляется из
   `pyproject.toml`. Ручное обновление версии в документах запрещено.
6. **Правило действует на каждом PR, а не только при релизе.** Изменение политики
   (allowlist, допустимые формы записи версии, источник версии) оформляется новым ADR;
   если меняются требования — новой версией ТЗ.

## 3. Последствия

- Живые документы не устаревают между релизами, а релиз не требует ручной правки версий
  в нескольких файлах.
- CI ловит хардкод на каждом PR; цена — эвристика и необходимость писать без литералов.
- Allowlist становится частью политики: расширение списка требует ADR, а не разовой правки
  скрипта.
- Исторические документы (CHANGELOG, session-log, ADR, замещённые версии ТЗ) остаются
  неизменными и проверкой не затрагиваются.
- Автоматического гейта на шапки ADR при смене версии ТЗ (`DOC121`) пока нет — это отдельная
  задача B-061, вне границ этого ADR.

## 4. Альтернативы

1. **Оставить правило только в release guide.** При обычных правках документации оно не
   видно, а CI-гейт остаётся без нормативной базы.
2. **Полностью запретить версии в документации.** Невозможно: CHANGELOG, ADR и история
   требований по определению содержат версии.
3. **Брать версию только из git-тега или `mike` и не проверять литералы.** Хардкод в
   документах остаётся незамеченным, расхождения возвращаются.
4. **Подставлять версию при сборке документации.** Не покрывает README, `AGENTS.md`,
   System Design и репозиторные документы вне `mkdocs`, то есть большую часть живых файлов.
