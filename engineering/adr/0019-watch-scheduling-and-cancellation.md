# ADR-0019: Watch: сериализация, max_delay и границы отмены

- **Статус:** принято
- **Дата:** 2026-11-20
- **Связанные документы:** [ТЗ v2.5 §8.5](../requirements/v2.5.md), [System Design §9](../system-design/index.md), [Roadmap 0.5.0](../roadmap.md), [ADR-0017](./0017-incremental-generation.md)

---

## 1. Контекст

`eggpipe watch` регенерирует артефакты при изменении источников. Текущая реализация
(`src/eggpipe/watch/watcher.py`): trailing debounce на `threading.Timer` (`_Debouncer`)
плюс флаги `_running`/`_pending` — событие во время прогона накапливается, после
завершения запускается ещё один прогон.

Три проблемы:

1. **Голодание.** Trailing debounce сдвигает прогон на каждом новом событии. При
   непрерывном потоке правок (интервал < `debounce_ms`) прогон откладывается
   бесконечно — пользователь не видит результат.
2. **Убийство прогона при выходе.** Прогон выполняется в daemon-потоке таймера.
   По Ctrl+C главный поток выходит из `WatchRunner.run()`, daemon-поток убивается
   при завершении процесса — возможно, посреди commit-фазы записи артефактов
   (`os.replace` по файлам из staging). Смешанное состояние и остаточные
   staging/lock вычищаются только следующим запуском (`_sweep_staging`,
   stale-lock detection). JSON Lines отчёт прогона не печатается.
3. **Мёртвая конфигурация.** `AppConfig.watch_debounce_ms` объявлен, но CLI `watch`
   использует собственный typer-default `300`; `EGGPIPE_WATCH_DEBOUNCE_MS` не
   действует. Расхождение с System Design §5.1 (AppConfig: CLI → env → .env →
   defaults).

Roadmap 0.5.0 (пункт 1): «батчинг файловых событий и отмена устаревших запусков —
серия правок даёт один прогон без параллельных сборок»; контракт CLI не меняется,
новой версии ТЗ не требуется.

Серия (burst) — последовательность файловых событий от первого необработанного
события до начала прогона, который их обрабатывает.

## 2. Решение

Фиксируются четыре инварианта планирования прогонов в watch:

- **G1 — сериализация.** В любой момент выполняется не более одного прогона.
  Параллельные сборки запрещены.
- **G2 — коалесцинг.** Серия событий даёт один прогон: каждое событие
  перезапускает debounce-таймер; одновременно существует не более одного
  запланированного прогона. «Отмена устаревших запусков» (Roadmap) означает отмену
  запланированного, ещё не начатого прогона, но не прерывание текущего.
- **G3 — ограниченная задержка (max_delay).** Прогон начинается не позже
  `max_delay_ms` от первого события серии, если runner свободен, и не позже
  `debounce_ms` после завершения текущего прогона, если события пришли во время
  него. `max_delay_ms = 10 × debounce_ms` (default: 3000 ms) — внутренний
  производный потолок; новой конфигурации и CLI-флагов нет.
- **G4 — актуальное состояние.** Каждый прогон читает файлы в момент своего старта.
  События во время прогона поднимают dirty-флаг; после завершения гарантирован
  ровно один follow-up прогон. Последний прогон серии всегда отражает актуальное
  состояние источников.

Границы отмены:

- **Запланированный прогон** — отменяется и заменяется (G2, G3).
- **Текущий прогон** — не отменяется: Engine завершает полный цикл
  (parse → validate → generate → write → manifest). Отменённый прогон оставил бы
  частично закоммиченные артефакты и неполный JSON Lines отчёт; точек отмены в
  Engine нет.
- **Остановка (Ctrl+C / `stop_event`).** Первый сигнал: отменить запланированные
  прогоны, дождаться завершения текущего, остановить Observer, exit 0. Повторный
  сигнал во время ожидания — немедленный выход, exit 130 (соответствует
  System Design §9.2: «прерывание по сигналу — 130»); остаточные staging/lock
  вычищает следующий запуск.

Конфигурация: в PR реализации CLI `watch` использует `AppConfig.watch_debounce_ms`
как источник default для `--debounce-ms` (приоритет CLI → env → .env → defaults);
`EGGPIPE_WATCH_DEBOUNCE_MS` начинает действовать. Новых полей нет.

Контракты: публичный API и CLI не меняются (`eggpipe.watch` — внутренний модуль);
поведение в рамках ТЗ v2.4 §8.5 уточняется, а не изменяется — новая версия ТЗ не
нужна. System Design §9 синхронизируется в PR реализации.

## 3. Алгоритм (design note)

### 3.1 `_Debouncer`: потолок max_delay

- Состояние серии: `_burst_start: float | None` (`time.monotonic()`).
- `trigger()`: если `_burst_start is None` — установить в текущий момент.
  Задержка таймера: `min(delay, max(max_delay − (now − _burst_start), 0))`;
  при неположительном остатке прогон планируется немедленно.
- `_fire()`: если прогон уже идёт (`_running`) — `_pending = True`, возврат
  (без сброса `_burst_start`). Иначе `_running = True`, `_burst_start = None`
  (окно серии закрыто — прогон отражает её события), выполнить callback, в
  `finally` при `_pending` — повторный `trigger()` (новое окно серии).
- `stop()`: устанавливает стоп-флаг, отменяет взведённый таймер и уведомляет
  ожидающих `wait_idle()`. После стоп-сигнала `trigger()` и повторный
  `trigger()` в `finally` `_fire()` подавляются; `_fire()`, уже стартовавший
  к моменту стоп-сигнала, возвращается без выполнения callback.
- `max_delay_ms` передаётся в конструктор: `WatchRunner` вычисляет
  `10 × debounce_ms`; `run_watch` получает параметр для тестов.

Свойство: событие во время длинного прогона сохраняет `_burst_start`, поэтому
follow-up после завершения прогона стартует практически сразу (остаток окна
истёк) — граница G3 «от первого необработанного события» выдерживается с
точностью до приоритета G1.

### 3.2 `WatchRunner.run()`: корректное завершение

- После `KeyboardInterrupt` или `stop_event`: `observer.stop()`, `observer.join()`,
  затем `_Debouncer.stop()` — отмена запланированных прогонов и подавление
  re-trigger (§3.1) — и ожидание завершения текущего прогона
  (`_Debouncer.wait_idle()` на `threading.Event`/condition: установлен, когда
  `_running == False` и таймер не взведён), затем return 0.
- Повторный `KeyboardInterrupt` во время `wait_idle()` не перехватывается —
  распространяется наружу, exit 130.
- Первичный `run_once()` на старте выполняется в главном потоке (как сейчас);
  Ctrl+C во время него — немедленное прерывание, exit 130.

### 3.3 CLI: wiring debounce

- `watch(debounce: Annotated[int | None, typer.Option("--debounce-ms", "--debounce")] = None)`;
  `debounce_ms = debounce if debounce is not None else AppConfig(...).watch_debounce_ms`.

## 4. Файлы и non-goals

Файлы PR реализации:

| Файл | Изменение |
|------|-----------|
| `src/eggpipe/watch/watcher.py` | `_Debouncer(max_delay)`, `wait_idle()`, shutdown в `run()` |
| `src/eggpipe/cli/main.py` | default `--debounce-ms` из `AppConfig` |
| `tests/test_watch.py`, `tests/test_watch_integration.py` | тестовая матрица (§5) |
| `engineering/system-design/index.md` §9 | синхронизация поведения |

Non-goals:

- per-entity watch (`watch --entity`) — не поддерживается в v2.4;
- отмена внутри Engine (cooperative cancellation) — см. §7.1;
- `watch_paths` плагинов и L2/L3 кэш — future (System Design §9.1, §9.3);
- новые config/CLI-параметры max_delay — только с ТЗ v2.5+.

## 5. Тестовая матрица

Тайминговые тесты используют малые значения (debounce ~50 ms, пропорциональный
max_delay), чтобы не замедлять suite.

| Сценарий | Ожидание | Инвариант |
|----------|----------|-----------|
| Серия из N событий в покое | Ровно один прогон после debounce | G2 |
| Событие во время прогона | Параллельных прогонов нет; ровно один follow-up | G1, G4 |
| Непрерывный поток (интервал < debounce) дольше max_delay | Прогон стартовал не позже max_delay от первого события | G3 |
| События во время длинного прогона | Follow-up не позже debounce после завершения | G3 |
| Остановка во время прогона | Прогон завершён, отчёт напечатан, exit 0; запланированные отменены | §2 |
| Ошибка в `run_once` | Watch продолжается | regression |
| `EGGPIPE_WATCH_DEBOUNCE_MS` без `--debounce-ms` | Значение применяется | §2 |

## 6. Последствия

- Критерий Roadmap 0.5.0 «серия правок не порождает параллельных запусков и
  лишних пересборок» закрыт инвариантами G1–G4.
- Худшая задержка отклика при непрерывном потоке ограничена: ~3.3 s сверх
  длительности прогона (default) вместо неограниченной.
- Ctrl+C больше не обрывает запись артефактов; цена — первый сигнал дожидается
  завершения прогона (длительная сборка задерживает выход; escape hatch —
  повторный Ctrl+C).
- `max_delay` не настраивается; если knob окажется нужен, это изменение контракта
  конфигурации — только через новую версию ТЗ.
- `EGGPIPE_WATCH_DEBOUNCE_MS` начинает действовать: поведение совпадает с
  System Design §5.1.

## 7. Альтернативы

1. **Отмена текущего прогона** (точки отмены в Engine между артефактами). Быстрее
   отклик на серии правок, но нарушает атомарность записи и контракт JSON Lines,
   усложняет ядро; корректность уже гарантирует G4 (follow-up прогон читает
   актуальное состояние). Отклонено; возможен пересмотр вместе с L2/L3.
2. **max_delay как config/CLI-параметр** (`--max-delay-ms`,
   `watch_max_delay_ms`). Гибкость, но меняет контракт CLI/конфигурации —
   требует ТЗ v2.5. Отклонено для 0.5.0.
3. **Фиксированная константа max_delay (2000 ms).** Не масштабируется с
   пользовательским `--debounce-ms`: при `--debounce-ms 5000` потолок ниже
   debounce противоречит намерению пользователя. Отклонено.
4. **Leading debounce** (прогон сразу по первому событию). Быстрая первая
   обратная связь, но прогон стартует на середине серии сохранений — лишние
   сборки и ошибки на неполном состоянии. Отклонено.
5. **Очередь событий с per-file гранулярностью и точечной пересборкой.** Требует
   L2/L3 кэша и per-entity watch (non-goal v2.4). Отклонено как future work.
