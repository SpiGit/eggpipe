# ADR-0021: Метрики L2 и structured logging

- **Статус:** принято
- **Дата:** 2026-11-24
- **Связанные документы:** [ТЗ v2.5 §8.7, §8.8, §10.8](../requirements/v2.5.md), [ADR-0014](./0014-beta-status-and-compatibility.md), [ADR-0017](./0017-incremental-generation.md), [ADR-0020](./0020-document-parse-cache.md), [System Design §5.3, §7.4, §8.7](../system-design/index.md), [Roadmap 0.5.0](../roadmap.md)

---

## 1. Контекст

Roadmap 0.5.0 п. 3 требует контракт метрик и structured logging до бенчмарков
(п. 4), потому что пороги регрессии должны опираться на стабильные поля отчёта.

Текущее состояние:

- `EngineReport` имеет `report_version: 2`; метрик кэша в нём нет.
- L2-кэш (ADR-0020) работает, но попадания и промахи видны только косвенно по
  `timings.parse_ms`; причины промахов не публикуются. ADR-0020 §9 явно отложил
  поля метрик и публикацию формата `.eggpipe/cache/` до ТЗ v2.5.
- Логирование (`config/logging.py`) умеет `text` и `log_format` — шаблон
  `logging.Formatter`; структурированного режима нет. Переиспользовать
  `log_format="json"` нельзя: это ломает совместимость существующего шаблона.
- B-050 собирает пакет изменений ТЗ: метрики, публикация кэша и актуальный
  `eggpipe_version` в примере manifest (B-041).

Потребители: CI-скрипты и бенчмарки (машинное сравнение), разработчики
(диагностика промахов кэша), пользователи (понятный лог в JSON-режиме).

## 2. Решение

1. **Отчёт `report_version: 3`.** Добавляется аддитивный блок `cache`; состав и
   семантика полей v2 не меняются. Версия повышается, чтобы потребитель с жёсткой
   проверкой схемы не принял неизвестные поля молча.
2. **Метрики L2 — сводные счётчики за прогон:** `hits`, `misses`,
   `miss_reasons` (`changed | missing | invalid | version`), `entries`, `bytes`.
   `cache: null`, когда L2 не используется.
3. **Structured logging** включается `log_mode: text | json`
   (`EGGPIPE_LOG_MODE`), default `text`. В `json` каждая запись — один JSON-объект
   в строке; обязательные поля `ts`, `level`, `logger`, `message`. Новый CLI-флаг
   не вводится.
4. **Формат `.eggpipe/cache/` публикуется как внутренний:** он описан в ТЗ
   §10.8 и версионируется `cache_version`, но не является публичным контрактом и
   не гарантирует совместимость между версиями Eggpipe.
5. **Совместимость:** `report_version: 2` больше не выдаётся. Потребители обязаны
   проверять точную версию и обновляться вместе с Eggpipe (beta-политика
   ADR-0014). В пределах v3 новые необязательные поля допускаются без смены версии
   только при сохранении семантики существующих.

Инварианты:

- Метрики не влияют на решение кэша и не меняют результат генерации.
- Ошибка записи лога не меняет exit code и не прерывает прогон.
- Метрики и логи не содержат секретов и абсолютных путей.
- Поведение по умолчанию (`text`, без incremental) не меняется.

## 3. Design note

### 3.1 Блок `cache` в отчёте

```json
"cache": {
  "hits": 7,
  "misses": 1,
  "miss_reasons": {"changed": 1, "missing": 0, "invalid": 0, "version": 0},
  "entries": 8,
  "bytes": 14336
}
```

- Счётчики относятся к фазе разбора: один документ — одно событие. Discovery и
  fingerprint, читающие мету без разбора, не считаются.
- `hits` — payload загружен из `docs/<sha256>.json`; `misses` — документ
  разобран заново по любой причине.
- `miss_reasons` взаимоисключающие; при конфликте приоритет:
  `invalid` → `version` → `missing` → `changed`.
- `entries`/`bytes` — состояние каталога на конец прогона; при `--plan` — на диске
  до прогона, потому что записи не создаются.
- Блок независим от `timings`: нулевой `parse_ms` не обязан означать hits, если
  incremental пропустил прогон целиком (L1) — в этом случае `cache: null`.

### 3.2 JSON-запись лога

```json
{"ts":"2026-11-24T10:03:02.145Z","level":"info","logger":"eggpipe.engine","message":"cache pruned","run_id":"01J...","event":"cache.prune","duration_ms":3,"extra":{"entries":8}}
```

- `ts` — RFC 3339 UTC с миллисекундами; `level` — нижний регистр; `logger` —
  имя логгера `eggpipe` / `eggpipe.<module>`; `message` — человекочитаемый текст.
- `event` — стабильное имя события; набор имён расширяется, переименование —
  изменение контракта (новая версия ТЗ).
- `extra` — только скаляры и вложенные объекты примитивов; запрещены секреты,
  `Path`, абсолютные пути.
- `exception` — текст трассировки отдельным полем, без встраивания в `message`.
- Запись идёт в `log_destination` (stderr по умолчанию); stdout не используется,
  кроме явного `log_destination: stdout`.
- `JsonLogFormatter` (переименован из `JsonFormatter`, чтобы не путать с output-форматтером
  отчёта) не бросает исключений наружу: при ошибке сериализации пишется
  минимальная запись `{"ts":...,"level":"error","logger":...,"message":"log serialization failed"}`.

### 3.3 Версионирование кэша

- `cache_version` повышается при изменении кодировки payload, схемы `meta.json`
  или правил валидности записи.
- `eggpipe_version` в мете — вторая граница: после обновления пакета записи
  промахиваются один раз.
- Несовпадение любой версии — промах с причиной `version`, не диагностика.
- Формат внутренний: сторонние инструменты не должны читать `docs/` и `meta.json`;
  поддерживаемый способ получить состояние — JSON-отчёт.

### 3.4 Совместимость отчёта

- v3 аддитивен к v2: новые поля только `cache`; `report_version` меняется на 3.
- Потребитель, ожидающий 2, должен явно отклонять 3 и обновиться; молчаливое
  принятие неизвестной схемы не поддерживается.
- Будущие аддитивные поля внутри v3 не требуют смены версии, если не меняют
  семантику существующих; удаление/переименование — только новая версия.

## 4. Файлы и non-goals

PR реализации (отдельно от этого ADR и ТЗ v2.5):

| Файл | Изменение |
|------|-----------|
| `src/eggpipe/engine/report.py` | `report_version = 3`, модель `CacheReport`, поле `cache` |
| `src/eggpipe/engine/document_cache.py` | счётчики hits/misses, причины промахов, entries/bytes |
| `src/eggpipe/engine/parser_cache.py`, `src/eggpipe/engine/engine.py` | передача счётчиков в отчёт |
| `src/eggpipe/config/app_config.py` | `log_mode: Literal["text", "json"] = "text"` |
| `src/eggpipe/config/logging.py` | `JsonLogFormatter`, выбор режима; ошибки не пробрасываются |
| `tests/test_report.py`, `tests/test_document_cache.py`, `tests/test_logging.py` | матрица §5 |
| `engineering/system-design/index.md` | синхронизация после реализации |
| `docs/ai/**` | пересборка при изменении публичной схемы отчёта |

Non-goals:

- per-document массив событий кэша в отчёте;
- Prometheus/OpenTelemetry и внешние экспортёры;
- новые CLI-флаги (`--log-mode`); режим задаётся только конфигом/env;
- вытеснение кэша по размеру сверх prune;
- гарантия совместимости `.eggpipe/cache/` между версиями;
- L3-кэш, пороги бенчмарков и CI-гейт по времени;
- новые `EGxxx` и изменения поведения по умолчанию.

## 5. Тестовая матрица

| Сценарий | Ожидание |
|----------|----------|
| Без `--incremental` | `cache: null`; остальные поля отчёта как в v2 |
| Холодный incremental-прогон | `misses = N`, `hits = 0`, причины `missing`; `entries/bytes > 0` |
| Повторный no-op incremental (L1 пропускает прогон) | `cache: null`, `generators[].status = "skipped"`; `parse_ms = 0` |
| Промах L1 без изменения документов (изменён `variables`/ресурс) | `hits = N`, `misses = 0`; `miss_reasons` все нули; `report_version: 3` |
| Изменён 1 из N | `hits = N-1`, `misses = 1`, причина `changed` |
| Битые `meta.json`/payload | Промах `invalid`, прогон успешен, диагностики не добавлены |
| Смена `cache_version`/`eggpipe_version` | Промах `version` |
| `--plan` | Метрики чтения заполнены, новые файлы не созданы, `entries/bytes` без изменений |
| `--entity`, `--check`, `--force`, `--clean`, `--strict` | `cache: null` |
| `log_mode=json` | Каждая строка — валидный JSON с обязательными полями; `run_id` совпадает с отчётом |
| `log_mode=text` | Вывод не изменился относительно v2.4 |
| Секреты и абсолютные пути | Отсутствуют в логах и `extra` |
| Сбой сериализации лога | Exit code и результат прогона не меняются |
| Инварианты отчёта | `hits + misses` и сумма `miss_reasons` равны числу документов фазы разбора |

## 6. Последствия

- CI и бенчмарки получают стабильные поля для порогов регрессии.
- Потребители `report_version: 2` обязаны обновиться; это допустимо в beta
  (ADR-0014) и фиксируется в CHANGELOG.
- Промахи кэша становятся объяснимыми без `--verbose`.
- JSON-логи пригодны для сбора и не ломают `--output-format json`.
- Стоимость: несколько счётчиков в горячем пути и отдельный formatter; влияния на
  результат генерации нет.

## 7. Альтернативы

1. **`log_format: "json"` как переключатель.** Конфликтует с существующим
   шаблоном `logging.Formatter`, невозможен без breaking-изменения AppConfig.
   Отклонено в пользу `log_mode`.
2. **Оставить `report_version: 2` и добавить поле.** Потребители со строгой
   схемой (`extra=forbid`) сломаются молча; явная версия честнее. Отклонено.
3. **Отдельный файл метрик или OTel-экспорт.** Лишняя зависимость и второй
   источник истины для CLI; для 0.5.0 достаточно отчёта и лога. Отклонено.
4. **Публичный контракт `.eggpipe/cache/`.** Зафиксировал бы внутреннюю
   реализацию и усложнил эволюцию; достаточно `cache_version` и промаха при
   несовпадении. Отклонено.
5. **Метрики уровня документа в отчёте.** Раздувают отчёт, раскрывают пути и
   порядок разбора; причины промахов в агрегате достаточны. Отклонено.
