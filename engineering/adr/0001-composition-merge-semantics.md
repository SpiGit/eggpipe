# ADR-0001: Семантика composition — merge при imports/extends

- **Статус:** принято
- **Дата:** 2026-11-10 (уточнено 2026-11-11 под ТЗ v1.2)
- **Связанные документы:** [ТЗ v1.2 §3.5](../requirements/v1.2.md), [System Design §4](../system-design/index.md)

---

## 1. Контекст

Модель данных может храниться в нескольких файлах (composition: monolith / file-per-entity / directory-per-entity). Файлы связываются через:

- `model.imports` — импорт YAML-моделей (композиция) и произвольных файлов (ресурсы для генерации, под именем `as`);
- `entity.extends` — наследование полей сущности от другой сущности внутри import-closure документа.

До v1.1 семантика слияния не была определена ("рекурсивный мерж по name"). Это самое рискованное место парсера: недоопределённость здесь порождает тихие, трудноуловимые баги (данные из чужого файла попадают в модель незаметно).

---

## 2. Принципы

1. **Merge происходит только по явным связям** (`imports`, `entity.extends`). Совпадение имён "само по себе" — это не merge, а ошибка валидации.
2. **Merge аддитивный**: слияние добавляет содержимое; замещение возможно только там, где оно явно указано (override в child).
3. **Детерминированность**: порядок применения импортов = порядок их объявления; результат стабилен между запусками (важно для diff-стабильности артефактов).
4. **Ошибки вместо молчаливых конфликтов**: любое неоднозначное совпадение → ошибка парсинга с указанием файла и пути импорта.
5. **Границы проекта**: импорты разрешаются только внутри project root (каталог `.mg.yaml`); выход наружу — ошибка (MG022), если явно не разрешён `--allow-outside-imports`.

## 3. Решения

| # | Вопрос | Решение |
|---|--------|---------|
| 1 | Сущность с тем же `name` приходит из двух мест, не связанных `extends` | **Ошибка.** Дубликаты имён сущностей/enum/type после композиции запрещены |
| 2 | Entity `extends`: поле с тем же именем есть и в parent, и в child | **Child переопределяет поле целиком** (замещение по имени, не "домердж" атрибутов) |
| 3 | Порядок полей после entity extends | Поля parent идут **в позиции parent**; переопределённые поля сохраняют позицию parent; новые поля child — в конце списка |
| 4 | Enum с тем же `name` из двух мест | Ошибка. Наследования enum нет |
| 5 | CustomType с тем же `name` из двух мест | Ошибка |
| 6 | Дубликат имени `as` у произвольных импортов | Ошибка (MG025) |
| 7 | Циклические импорты | Ошибка с полным путём цикла: `a.yaml → b.yaml → a.yaml` (MG006) |
| 8 | Ограничение глубины импортов | Лимит 10 (MG006) |
| 9 | Сломанный/несуществующий импортируемый файл | Ошибка парсинга с путём, где объявлен импорт |
| 10 | Ссылка кастомных типов на несуществующий `base` | Ошибка валидации модели (после композиции) |
| 11 | Импортированные YAML-файлы — валидируются? | Да: каждый импортированный документ валидируется как модель и обязан иметь **тот же `format`** и совместимую `version` |
| 12 | Произвольные импорты (не YAML) | Файл читается как bytes и доступен в контексте генерации под именем `as`; merge не участвует |
| 13 | Один и тот же resolved-путь импортируется/указан несколько раз | Обрабатывается **один раз**, повторного merge нет; при дублях в `sources` — Warning MG024 |
| 14 | `entity.extends` по короткому имени при нескольких кандидатах | Неоднозначность → ошибка MG009; рекомендуемая форма — `{import: alias, entity: Name}` |
| 15 | Цикл или глубокая цепочка `extends` | Ошибка MG009 (глубина > 10) |
| 16 | `metadata` при импорте/extends | **Не мержится**: остаётся у своего документа/сущности/поля |

### 3.1. Entity extends — merge полей

```
parent:  [id, created_at, updated_at]         # импортируемые общие поля
child:   extends: parent + [title, id(override)]
result:  [id(override), created_at, updated_at, title]
                                            # ^ override занимает позицию parent-поля
```

Короткая и явная формы:

```yaml
# короткая: родитель ищется по уникальному имени в import-closure
extends: AuditFields

# явная: рекомендуется при нескольких кандидатах
extends:
  import: audit        # alias YAML-импорта
  entity: AuditFields
```

Мержатся только `fields`. Поля, объявленные только в child, добавляются **в порядке объявления** в конец. Атрибуты поля child (type, required, nullable, default, constraints) заменяют родительские **целиком** — частичный override атрибутов не поддерживается (явность важнее удобства). `description`, `version`, `updated_at`, `metadata` child'а не наследуются от parent'а.

### 3.2. Composition между source-файлами (file-per-entity и т.п.)

Каждый source-файл — самостоятельный документ модели. Ядро собирает финальную модель из всех `sources` метаконфига: union entities/enums/types. Совпадение имён между source-файлами (не связанными extends) — ошибка валидации (та же таблица, решение #1).

`entity.extends` разрешается **только внутри import-closure своего документа**: сущность из другого `source`, не импортированная явно, родителем быть не может (MG009).

## 4. Алгоритм (скетч)

```
1. parse_document(path) → ModelDocument(header format+version, imports, model)
2. resolve_imports(document):
     DFS по document.imports:
       - canonical path cache: один документ — один раз (решение #13)
       - track visiting-stack → цикл = ошибка (полный путь, MG006)
       - depth > 10 → ошибка (MG006)
       - project root check → MG022
       - YAML-документ → рекурсивно resolve, затем merge (решения #1–#5)
       - произвольный файл → регистрация в imports-map под `as` (решение #6)
3. resolve_extends(document):
     для каждого entity с extends:
       родитель ищется в import-closure документа (short name или {import, entity})
       цепочка разрешается рекурсивно; цикл/depth > 10 → MG009
       merge полей по решениям #2–#3
4. merge sources → SourceModel; дубликаты имён после merge — MG002
5. validator.py — семантика; тип/constraints/default проверяются отдельно
```

Мерж по полям детерминирован: сначала parent (в порядке объявления), потом override на месте, потом новые поля child.

---

## 5. Последствия

**Плюсы:**
- Никаких "тихих" слияний: любое неоднозначное совпадение обнаруживается на этапе парсинга с точным указанием ошибки.
- Diff-стабильность артефактов: детерминированный порядок полей и импортов.
- Правила простые и предсказуемые: "merge = add, override = явно".

**Минусы / trade-offs:**
- Автоматического "умного" мержа нет: пользователю придётся явно переопределять поле целиком при частом наследовании. Ожидаемо приемлемо: общие поля (audit/id) наследуются без override.
- Дубликат `name` между несвязанными файлами = ошибка даже если это "две разные версии одной сущности" — это осознанный запрет, а не упущение.

## 6. Открытые вопросы (future)

- Повторное использование merge между разными форматами (format-плагины могут добавлять свои правила поверх — пока не поддерживается).
- Более гранулярный merge metadata (сейчас `metadata` не мержится: остаётся у своего документа/сущности/поля).
