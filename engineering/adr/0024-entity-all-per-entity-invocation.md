# ADR-0024: `--entity-all` — per-entity вызов для всех entities

- **Статус:** принято
- **Дата:** 2026-11-27
- **Связанные документы:** [ТЗ v2.6 §6.1.2, §8.2, §10](../requirements/v2.6.md), [ADR-0018](./0018-per-entity-generation.md), [ADR-0004](./0004-ownership-manifest-cleanup.md), [ADR-0009](./0009-global-manifest-ownership.md)

---

## 1. Контекст

В полном прогоне `eggpipe generate` собирает один `ModelSlice` со всеми entities и вызывает
каждый генератор один раз. Это соответствует контракту: `output_scope="entity"` объявляет
совместимость генератора с per-entity режимом, но не переключает режим запуска. Режим
включается только явным выбором `--entity` / `entities=...` (ADR-0018).

Для модели из десятков entity (например, один YAML-файл или каталог на таблицу) нужен
вызов генератора отдельно на каждую entity. Сейчас есть два пути:

- перечислить все имена в `--entity`, что быстро устаревает и неудобно при росте модели;
- итерироваться по `model.entities` внутри генератора, что заставляет автора плагина
  знать особенность полного прогона и смешивает ответственность ядра и плагина.

Glob-маски (`*`, `lu_*`) в `--entity` не поддерживаются: `--entity` принимает точные имена
после композиции, а shell-подстановка работает с файлами, а не с именами entity. Добавлять
маски в существующий флаг опасно: они меняют смысл явного выбора и требуют отдельной
политики экранирования и пересечения с `generators[].input`.

Нужен явный режим «вызвать генератор по одной entity для всех entities», не меняющий
поведение обычного `generate`.

## 2. Решение

Добавить явный opt-in режим:

- CLI: `eggpipe generate --entity-all`.
- API: `Engine.build(entity_all=True)`, `Engine.generate(entity_all=True)`,
  `Engine.check(entity_all=True)`.
- `--entity-all` несовместим с `--entity`; в CLI это usage error (exit 2), в API —
  `ConfigValidationError`.
- `entity_all=True` несовместим с `entities`; `entities=None` + `entity_all=False` —
  обычный полный прогон.

Режим переиспользует семантику per-entity из ADR-0018:

- выбор применяется после композиции;
- все выбранные генераторы обязаны иметь `output_scope="entity"`, иначе `EG303`, exit 2;
- manifest location дополняется, cleanup отключён (+ Warning EG030);
- incremental не используется;
- watch с `--entity-all` не поддерживается.

Дополнительно:

- Порядок вызовов — порядок entities в итоговой модели.
- Если `generators[].input.entities` задан, множество вызовов — пересечение с этим списком;
  имена `input` валидны против итоговой модели, поэтому пересечение непусто.
- Каждый вызов получает `ModelSlice` ровно с одной entity.
- `--entity` сохраняет прежнюю семантику: явно выбранная entity вызывает генератор даже
  при пустом пересечении с `input`.
- Ошибка одного вызова не останавливает остальные entities и генераторы; diagnostics
  собираются по всем вызовам. При любой ошибке запись не выполняется (exit 1).
- Пути, повторяющиеся между вызовами одного генератора, — `EG042`.
- В отчёте остаётся один `generators[]` на генератор: `duration_ms` — суммарное время,
  `formats` — объединение форматов, `artifacts` — все артефакты, `status="error"` при
  ошибке любого вызова. `report_version: 3` не меняется; diagnostics содержат
  `location.entity`.
- `--entity-all` на модели без entities — `EG018`, exit 1.

## 3. Manifest, cleanup и incremental

Изменений в ownership нет: location остаётся `(generator, output_dir)`. Каждый вызов
дополняет location, как `--entity`; артефакты других entities сохраняются. Cleanup и
incremental отключены независимо от конфига и флагов. Полный прогон или `eggpipe clean`
реконсилируют manifest, как и для обычного per-entity режима.

## 4. Отчёт и диагностика

Формат отчёта не меняется. Агрегация вызовов в один `generators[]` сохраняет обратную
совместимость `report_version: 3` и не требует новых полей. Диагностики, возникшие при
вызове конкретной entity, получают `location.entity`; это позволяет отличить ошибки
разных вызовов без изменения схемы отчёта.

Новых диагностических кодов нет:

- `EG018` — пустая модель при `--entity-all`;
- `EG303` — генератор не объявил `output_scope="entity"`;
- конфликт `--entity`/`--entity-all` — usage error, exit 2.

## 5. Последствия

- Автор генератора с `output_scope="entity"` получает ровно одну entity на вызов и не
  обязан итерироваться по `model.entities` в полном прогоне.
- Обычный `eggpipe generate` не меняется: полный `ModelSlice`, один вызов.
- Появляется явный способ перебрать все entities без внешнего shell-цикла и повторного
  парсинга модели.
- Режим требует новой версии ТЗ (v2.6) и реализации в CLI/Engine; до реализации
  существующие `--entity` и итерация по `model.entities` остаются рабочими.
- Glob-маски, auto-split по `output_scope` и per-entity watch остаются future.

## 6. Альтернативы

1. **Автоматический split при `output_scope="entity"`.** Отклонено: меняет семантику
   полного прогона, cleanup, manifest и поведение существующих генераторов; требует
   отдельного breaking-решения и ADR.
2. **Glob-маски в `--entity`.** Отклонено в этом решении: `--entity-all` покрывает основной
   сценарий без неоднозначности `*`, экранирования и shell-подстановки. Маски можно
   добавить отдельно, если появится сценарий подмножества (`lu_*`).
3. **Новые раскладки `file-per-entity`/`directory-per-entity`.** Отклонено: раскладки
   описывают композицию источников, а не число вызовов генератора; существующие
   `file-per-model`/`directory-per-model` уже означают одну модель на файл/каталог.
4. **Shell-цикл `--entity` для каждого имени.** Отклонено как штатный путь: требует
   внешнего списка имён, повторно парсит модель и отключает incremental на каждом запуске.
