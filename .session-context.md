## Принятые решения

### Pydantic для всех внутренних моделей
- Все dataclasses заменены на Pydantic BaseModel
- Валидация встроена в модели (Field.type, Entity.name, etc.)
- YAML → Model: `model_validate(yaml_data)`
- Поддержка aliases (kebab-case YAML → snake_case Python)
- Убран отдельный validator.py — валидация в моделях

### Структура документа модели (header)
- `format` — **классификатор для парсера** (какой парсер использовать), **не привязан к генераторам**
- `extends` — родительский тип для наследования
- `version` — версия **схемы формата** (не версия модели!)
- `updated_at` — дата изменения в ISO 8601

### Универсальная базовая схема `entity-model`
- Без SQL/API-специфики: только entities, enums, types
- SQL-концепции — через наследование в пользовательских типах

### Композиция данных (Composition)
- 3 варианта хранения: monolith, file-per-entity, directory-per-entity
- Imports YAML-моделей: композиция, наследование
- Imports произвольных файлов: для использования при генерации (иконки, шаблоны, etc.)
- Правила: относительные пути, циклические импорты запрещены

### Принцип: данные отделимы от генерации
- Модель — просто данные
- Метакогфиг определяет: откуда что брать и куда генерировать
- Гибкий `input` в генераторе: выбор подмножества entities/enums/types

### Нет встроенных генераторов
- Все создаются под проект/стек (Oracle, Snowflake, etc.)
- Детали реализации (плагины, шаблоны) — в документации разработчика, не в ТЗ

### CLI-гибкость
- `mg generate` — все модели + все генераторы
- `mg generate model.yaml` — конкретная модель + все генераторы
- `mg generate model.yaml -g gen1` — конкретная модель + конкретные генераторы
- `mg generate -g gen1` — все модели + конкретные генераторы
- Список генераторов: через запятую или повторяющиеся флаги (-g)

### Разделение конфигурации
- **AppConfig (technical):** логирование, пути, debug mode, env vars → .env → файл → defaults
- **GeneratorRules (`.mg.yaml`):** модели, генераторы (ранее BusinessConfig)
- Слово "Config" не используется в нейминге бизнес-логики во избежание путаницы

### Архитектура
- Ядро (metadata-generator): CLI, парсинг, валидация, composition, engine
- Плагин (генератор): отдельный пакет с кодом + шаблонами

### Архитектура плагинов (уточнено 2026-11-10)
- Подключение через entry points в `pyproject.toml`
- Все плагины реализуют общий интерфейс `GeneratorPlugin`
- Плагин на вход получает модель сущности (`EntityModel`)
- Плагин на выходе возвращает произвольный текст (любые файлы)
- Стандартных генераторов "из коробки" нет — может быть отдельный проект в будущем

## Решения сессии 2026-11-10

### Режимы использования

metadata-generator может использоваться двумя способами:

#### 1. Как CLI-инструмент
```bash
pip install metadata-generator
mg generate model.yaml
mg watch model.yaml
```

#### 2. Как библиотека
```python
from metadata_generator.core import Engine
from metadata_generator.config import AppConfig

# Programmatic API
engine = Engine(config)
results = engine.generate()
```

#### 3. Как библиотека + CLI (основной сценарий для бизнес-проектов)

**Сценарий:** Есть проект N, которому нужен специфический генератор объектов.

1. Проект N подключает metadata-generator как библиотеку:
   ```toml
   # pyproject.toml проекта N
   [project]
   dependencies = ["metadata-generator"]
   ```

2. В проекте N пишутся плагины генерации для нужд этого проекта:
   ```python
   # my_project/plugins/__init__.py
   from metadata_generator.core import GeneratorPlugin
   
   class MyProjectGenerator(GeneratorPlugin):
       def generate(self, entity, context):
           # Специфичная логика для проекта N
           return [...]
   ```

3. Плагины регистрируются через entry points:
   ```toml
   # pyproject.toml проекта N
   [project.entry-points."metadata_generator.generators"]
   my-project = "my_project.plugins:MyProjectGenerator"
   ```

4. Запуск возможен как из CLI, так и программно:
   - CLI: `mg generate` — использует плагины из entry points
   - Library: `engine.generate()` — тот же результат

**Примеры таких инструментов:** ruff, pytest, mypy — это библиотеки с CLI.

### Нейминг
- `BusinessConfig` → `GeneratorRules` (класс)
- `BusinessConfigLoader` → `GeneratorRulesLoader` (лоадер)
- `business_config.py` → `generator_rules.py` (файл)
- Причина: слово "Config" создаёт путаницу с AppConfig

### Логирование (добавлено в System Design)
- Добавлена секция 5.3 "Настройка логирования"
- Реализация: `setup_logging()`, `get_logger()`
- Поддержка: stderr, stdout, file:path
- Ротация файлов через `RotatingFileHandler`
- Приоритет источников конфига: env vars → .env → defaults
- Добавлен файл `config/logging.py` в структуру проекта

### Plugin architecture
- Entry points: `metadata_generator.generators`
- Базовый интерфейс: `GeneratorPlugin`
- Вход: `EntityModel`, выход: `list[GeneratedFile]`
- Все плагины наследуют общий Protocol/Abstract class
