## Принятые решения

### Pydantic для всех внутренних моделей
- Все dataclasses заменены на Pydantic BaseModel
- Валидация встроена в модели (Field.type, Entity.name, etc.)
- YAML → Model: `model_validate(yaml_data)`
- Поддержка aliases (kebab-case YAML → snake_case Python)
- Убран отдельный validator.py — валидация в моделях

### Структура документа модели (header)
- `format` — **классификатор для парсера** (какой парсер использовать), **не привязан к генераторам**
- `extends` — родительский тип для наследования
- `version` — версия **схемы формата** (не версия модели!)
- `updated_at` — дата изменения в ISO 8601

### Универсальная базовая схема `entity-model`
- Без SQL/API-специфики: только entities, enums, types
- SQL-концепции — через наследование в пользовательских типах

### Композиция данных (Composition)
- 3 варианта хранения: monolith, file-per-entity, directory-per-entity
- Imports YAML-моделей: композиция, наследование
- Imports произвольных файлов: для использования при генерации (иконки, шаблоны, etc.)
- Правила: относительные пути, циклические импорты запрещены

### Принцип: данные отделимы от генерации
- Модель — просто данные
- Метакогфиг определяет: откуда что брать и куда генерировать
- Гибкий `input` в генераторе: выбор подмножества entities/enums/types

### Нет встроенных генераторов
- Все создаются под проект/стек (Oracle, Snowflake, etc.)
- Детали реализации (плагины, шаблоны) — в документации разработчика, не в ТЗ

### CLI-гибкость
- `mg generate` — все модели + все генераторы
- `mg generate model.yaml` — конкретная модель + все генераторы
- `mg generate model.yaml -g gen1` — конкретная модель + конкретные генераторы
- `mg generate -g gen1` — все модели + конкретные генераторы
- Список генераторов: через запятую или повторяющиеся флаги (-g)

### Разделение конфигурации
- **AppConfig (technical):** логирование, пути, debug mode, env vars → .env → файл → defaults
- **GeneratorRules (`.mg.yaml`):** модели, генераторы (ранее BusinessConfig)
- Слово "Config" не используется в нейминге бизнес-логики во избежание путаницы

### Архитектура
- Ядро (metadata-generator): CLI, парсинг, валидация, composition, engine
- Плагин (генератор): отдельный пакет с кодом + шаблонами

### Архитектура плагинов (уточнено 2026-11-10, v1.1)
- Подключение через entry points: `metadata_generator.generators` (генераторы) и `metadata_generator.formats` (форматы)
- Все генераторы реализуют интерфейс `GeneratorPlugin` с проверкой `api_version`
- Вход генератора — `GeneratorInput`: цельный срез модели (`SourceModel`) + `GenerationContext` + `GeneratorConfig`
- Выход: `GenerationResult` со списком `Artifact` (относительный путь задаёт плагин)
- Локальные плагины — через editable install; sys.path-хаки и plugins_dir не поддерживаются

## Решения сессии 2026-11-10 (третья: ревью → ТЗ v1.1)

Ревью ТЗ v1.0 и System Design породило серию решений, зафиксированных в ТЗ v1.1 и ADR-0001.

### Модель
- **Сущности изолированы**: никаких relations в базовой модели. Взаимосвязь — по необходимости отдельная сущность-связка (вне текущего скоупа).
- **Заголовок документа**: только `format` + `version`. Поле `extends` убрано — принадлежность формата и его наследование задаёт формат-плагин.
- **`updated_at`/`version`** — на уровне **entity** (трекаем изменение именно сущности). Дата полезна для вставки в артефакт (без git-дифф шума), но обновляется вручную → добавлена warning-валидация (устаревшая дата) + future provenance-утилита (git-дата/хеш).
- **`default` без `auto`**: только скаляры. Автогенерация (`identity`, `uuid4()`, `now()`) — зона формата/генератора (напр. `sql-model`).
- **Null-матрица** (ТЗ §3.6): 4 валидных состояния required×nullable×default + запрещённые комбинации (validation errors) + `required=true&nullable=true` → warning (для future PATCH-семантики). `nullable` по умолчанию `false`.

### Форматы
- Формат определяет **плагин** (FormatPlugin). Реестр форматов. Встроен только `entity-model`.
- Формат-плагин: имя(-а) формата, поддерживаемые версии, доп. поля схемы, своя валидация.

### Композиция / merge
- Правила зафиксированы в **ADR-0001**: merge только по явным связям (`imports`/`entity.extends`), аддитивный, детерминированный, конфликты имён — errors; entity extends — замещение поля целиком, позиции parent-полей, новые child-поля в конце; глубина ≤ 10; циклы → ошибка с полным путём.

### Плагины
- **Вход — цельный срез модели** (`GeneratorInput`), а не одиночная entity: нужны cross-entity артефакты (barrel-файлы, миграции, общие enums).
- **Выход** — `Artifact(path=относительный POSIX-путь, content=str)`. Имена файлов определяет плагин; ядро валидирует нормализацию и границы `output_dir`. mime-type убран.
- **AppConfig плагину не передаётся** — публичный контракт чистый (`GenerationContext` содержит vars, naming hint, imported files, source paths).
- **`api_version: Literal["1"]`** — проверка совместимости при загрузке; публичный API ядра экспортирует только контракты.
- **Локальные плагины только через `pip install -e`** — никаких `sys.path` хаков и `plugins_dir`.

### Naming / file_naming
- Канонические имена в модели никто не переименовывает.
- `defaults.naming_convention` — **подсказка**: ядро предоставляет `NamingStyle` + `transform()`, плагин решает, что и куда применять.
- `file_naming` — зона плагина (опция в `options`), не ядро: путь артефакта задаёт плагин.

### Запись артефактов
- `on_conflict: overwrite (default) | skip | error` — параметр генератора.
- Атомарная запись: staging dir → move.
- Манифест `.mg-manifest.json` в output_dir после успешного запуска.
- Cleanup осиротевших файлов (только по манифесту): `cleanup: off | prompt | enabled` + разовый `--clean`.

### CLI
- Единый подкомандный стиль: `mg config show`, `mg config validate`, `mg model validate`, `mg gen list`; `generate`, `watch`, `init` — top-level.
- `--strict` (warnings → errors), `--format text|json`.
- `--var KEY=VALUE`: CLI > `variables:` в `.mg.yaml`; доставка через `GenerationContext.variables`; ядро никогда не применяет vars молча — решает плагин.
- Exit codes: 0 успех / 1 errors (или strict warnings) / 2 config-usage. При падении одного генератора остальные продолжаются.

### Прочие зафиксированные вещи
- Единая точка логирования: `config/logging.py` (дубликат `utils/logging.py` убран).
- CLI-вывод (rich) не смешивается с логами: логи stderr/file, чтобы не ломать `--format json`.
- `PRIMITIVE_TYPES` = Literal из 10 типов, точно по ТЗ §3.2 (string, text, integer, bigint, boolean, float, date, datetime, uuid, json).
- Кэшированные entity/enum-индексы через `model_validator(mode="after")` + PrivateAttr.
- watchdog — lazy import.
- Golden-file тесты — главный щит регрессии артефактов; property-based переформулировано (parser не падает на любом dict; round-trip).
